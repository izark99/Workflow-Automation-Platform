# Decisions

Newest last.

## D1 Playwright uses the preinstalled Chromium (T0.1)

`@playwright/test` is pinned to 1.63.0, the version of the preinstalled `playwright`.
That version finds the bundled Chromium in `/opt/pw-browsers`, so no browser download
and no `playwright install` is needed. System Chrome is not used.

## D2 TypeScript 6.0.3, not 7 (T0.1)

`typescript-eslint` 8.73.0 accepts TypeScript `>=4.8.4 <6.1.0`. TypeScript 7 is the latest
release but would break lint, so the project pins 6.0.3. Revisit when typescript-eslint
supports 7.

## D3 Exact versions (T0.1)

`.npmrc` sets `save-exact=true` and `package-lock.json` is committed, so `npm ci` is
reproducible for `npm run gates`.

## D4 Gate scripts not built yet (T0.1)

`spike`, `test:acceptance`, `test:e2e`, `test:ui-rules` and `test:db` run
`scripts/not-implemented.mjs`, which exits 1 and names the task that replaces it.
`vitest` runs only `src/**/*.test.ts(x)`. Playwright specs live in `e2e/`.

## D5 Benchmark files count the header row (T0.2)

"1,048,576 rows" is the Excel limit including the header, so the largest files hold the
header plus 1,048,575 data rows. The other sizes use the same rule. The generator is
seeded, writes shared strings like Excel, and runs as TypeScript with Node's built-in type
stripping (`node scripts/generate-bench-files.ts`), so it needs no extra dependency.

## D6 SheetJS from its own CDN (T0.3a)

`xlsx` is installed from `https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz`, the
official install path in the SheetJS docs. 0.20.3 is the newest release on that CDN
(0.20.4 and later return 404). The npm `xlsx` package is stale and is not used.

## D7 DuckDB-WASM bundles are self-hosted (T0.3a)

The worker selects the `mvp` or `eh` bundle through Vite `?url` imports, not
`getJsDelivrBundles()`. A run therefore loads only static assets from this app, which the
no-network test in T1.20 needs. These bundles need no COOP/COEP headers.
`@duckdb/duckdb-wasm` is pinned to 1.33.1-dev57.0 (the `latest` tag) and `apache-arrow`
to 17.0.0, the version it depends on.

## D8 Spike measures a production build (T0.3a)

On a cold start the Vite dev server re-optimizes dependencies and reloads the page, which
failed one smoke run. The spike runner (T0.3b) builds the app and serves it with
`vite preview`. This also removes dev transforms from the measurements.

## D9 Own streaming xlsx reader for large files (T0.4a)

SheetJS whole-workbook parsing returns no sheet for the 500k and 1M row xlsx files (T0.3b).
`src/engine/xlsx-stream/` reads xlsx as a stream instead: zip directory by slices,
`DecompressionStream('deflate-raw')` per part, rows parsed in chunks. It adds no dependency.
Known limits, each reported with a "save as csv" message: zip64 parts and compression
methods other than stored or deflate. The 1904 date system is not handled. SheetJS stays
the reader for small files and the writer for output (T1.15).

## D10 Reading strategies chosen by the spike (T0.4b)

`docs/SPIKE_RESULTS.md` is generated by `npm run spike`, and the choice is a rule over the
numbers: the strategy that finishes at the most file sizes, then the lower total load time.
On the T0.4b run this gave `xlsx-stream` for xlsx and DuckDB `read_csv` on the file handle
for csv. SheetJS whole-workbook parsing stays only for small files and for writing output.
It returns "no sheet" without an exception for the 500k and 1M row xlsx files, and it needs
about 10 GB of renderer memory for the 1M row csv.

## D11 Size guard (T0.5)

- The limit `MAX_SAFE_XLSX_BYTES` (300,002,342) is the exact byte size of the largest xlsx that
  loaded in the spike. Files above it are refused before any parsing, with the "save as csv"
  message from `src/ui/strings.ts`. A test fails if the limit is above the largest size in
  `docs/spike-raw.json`.
- csv is not guarded. DuckDB reads it from the file handle: 378 MB took 1.1 GB of peak memory.
- Until T1.3 (input node) and T2.16 (run screen) exist, the guard is enforced only on the
  benchmark page. Both tasks now say they must call it.
- Known limit: the limit comes from a synthetic file with a pool of 2,000 distinct strings.
  A real xlsx under the limit with many distinct strings keeps its whole shared-strings table
  in memory, and this was not measured. Re-measure with real data when it is available.
- If a later spike run fails on the 1,048,576-row xlsx, `npm run check` turns red through the
  limit test. That is intended: re-measure and set the limit again. Do not loosen the test.

## D12 Flow definition envelope and ports (T1.1)

- The flow JSON follows React Flow: `nodes[{id, type, label?, position?, settings}]` and
  `edges[{source, sourceHandle?, target, targetHandle?}]`, plus `schemaVersion: 1`. Phase 2 needs no conversion.
- Ports live in one registry (`NODE_PORTS` in `src/engine/flow/types.ts`). Filter has outputs `match` and
  `nomatch`. Lookup has inputs `left` (required) and `right` (only for a lookup on another node; a reference
  table is named in the settings, never by version). Append and SQL take `in1`, `in2`, ... with no gap, and the
  number gives the order, not the position of the edge in the array. Missing handles default to the first one.
- The validator is hand-written (`src/engine/flow/validate.ts`), not `ajv`, so no dependency outside the stack
  is added. `flowJsonSchema` documents the envelope and a test keeps its node type list equal to `NODE_TYPES`.
  Settings of each node type are validated by the module of that type, task by task.
- Input nodes will bind to files by a logical key in their settings (for example "Timesheet"), not a file name,
  because file names differ per dataset.

## D13 Plan notes for the engine tasks (T1.1)

Open design points to settle in the task that needs them, each recorded here when decided:

- Row order (R12): DuckDB does not keep order through joins and group-bys. Sorting is a setting of the Output
  node (T1.15), not a separate node.
- Summary header (R10): the `*_days` and `ot_*_hours` columns follow reference table order, including zero
  columns, so Pivot (T1.13) needs a column list taken from a reference table, a fill value and a suffix.
- Input typing (R8): a mixed OT column keeps text such as `2h` as text. Type inference must not turn it into NULL.
- Identifiers are always quoted. Check whether DuckDB treats quoted names as case-insensitive and record what
  the engine enforces (CLAUDE.md wants case-sensitive column names).
- Dates leave the engine as UTC-safe values, and the acceptance spec runs with a UTC+7 time zone, so that a
  date does not move by one day.
- Fixture employee IDs must not appear in any `src/` file, tests included. The acceptance harness lives outside `src/`.

## D14 Engine core: runner, tables, column names (T1.2)

- The engine talks to DuckDB only through `SqlRunner` (`exec`, `query`, `cancel`, `close`). Two builds of the
  same DuckDB-WASM: `createNodeRunner` (Node blocking API, used by unit tests, checked to run under Vitest) and
  `createBrowserRunner` (Web Worker, used by the app). No extra dependency, no `@duckdb/node-api`.
- Every output of every node is stored as a table (`CREATE TABLE ... AS`), not a view, so a node with two
  consumers runs once. Tables carry a per-run prefix, and `dispose()` drops them.
- Node modules are synchronous: settings and input columns in, a SELECT and the exact output columns out. The
  engine tracks columns in JavaScript. This is how names stay case-sensitive: measured on DuckDB 1.5.4, a quoted
  `"a"` resolves to a column `"A"`, so `requireColumn` checks names before any SQL is built.
- Cells leave the engine as numbers (cast to DOUBLE), ISO date text (`strftime`) and text, so a date never goes
  through a JavaScript Date and cannot move by a day in another time zone.
- Cancel: the signal is checked between steps and calls `runner.cancel()`. The Node runner cannot stop a query
  that is already running; the browser runner calls `cancelSent()`.
- `TRY()` and `try_cast` exist in this DuckDB version (checked for T1.6).

## D15 Input file node (T1.3)

- Settings: `key` (logical name, one file per key, unique in a flow), `sheet`, `headerRow` (from 1, default 1),
  `skipRows` after the header, `fillDown` (column names), `rowNumberColumn` (name of an added column with the row
  number in the file; none by default). The file is read before the nodes run (`loadInputFile`); the node module only
  exposes the loaded table. `runFlow` takes `files` by key, and `inputs` for tables already in memory (tests).
- Every cell is staged as text in DuckDB and cast afterwards. xlsx column types come from the cell kinds seen while
  streaming: all numbers give number, all midnight dates give date, all booleans give boolean, anything else (mixed or
  text) stays text with numbers written as plain text. So `2h` among numbers survives (rule R8). csv columns are
  number only for plain decimals without leading zeros, date only for `YYYY-MM-DD`, otherwise text. The Column mapping
  node (T1.4) is where a user retypes a column.
- Fully blank rows are skipped. Trailing empty header cells are dropped, interior ones are named `Column N`, a
  duplicate header name is an error. For csv, `headerRow` counts non-blank lines, because DuckDB skips blank lines.
- Known limit: rows are staged with SQL INSERT in batches of 2,000. This is correct but slower than an Arrow insert.
  Throughput on a 1,000,000-row xlsx is not measured; measure it in T2.16 and switch the staging step if needed.
- Dates read from xlsx are built from UTC milliseconds, so they do not move with the time zone of the browser.

## D16 Column mapping node (T1.4)

- Settings: `columns: [{source, keep?, name?, type?}]`, one row per source column, in output order. `keep` defaults to
  true. Columns the grid does not list stay unchanged and follow the listed ones, so a flow keeps working when a file
  gains a column. Drop a column explicitly with `keep: false`.
- Conversions: any type to text (numbers without a trailing `.0`, dates as ISO text); text to number, date or boolean
  (empty text becomes NULL, a bad value fails the step and names the value); boolean to number; number to boolean
  (non-zero). Number to date and date to number are refused with a hint to use a Formula column.
- Two output names that differ only by case are refused, since one DuckDB table cannot hold both (see D14).
- `src/engine/nodes/test-helpers.ts` runs one node on in-memory tables through `runFlow`, for node unit tests.

## D17 Formula language: typing, blanks and errors (T1.6, advisor-reviewed)

- Pipeline: lexer and parser (`src/engine/formula/parse.ts`) give an AST with source positions. The compiler (T1.6b)
  turns it into DuckDB SQL plus a type (`text`, `number`, `date`, `boolean`), checked against the input columns.
  Type mismatches and non-boolean Filter conditions are compile errors with a position.
- Excel precedence: comparison, then `&`, then `+ -`, then `* /`, then `^` (left-associative: `2^3^2 = 64`), then
  unary minus (tighter than `^`: `-2^2 = 4`). Function names ignore case. Column references `[name]` do not.
- Errors are NULL, nothing throws at run time: `/` is `x / NULLIF(y, 0)`, `VALUE` and `DATE` use `TRY_CAST`.
  `IFERROR(x, alt)` is `COALESCE(x, alt)`. Two divergences from Excel, documented and not tested as Excel results:
  `IFERROR` on a bare blank reference returns `alt` (Excel gives 0), and `ISBLANK` of an error is TRUE. Use
  `ISNUMBER(VALUE(x))` to test a number, as `ISNUMBER(text)` is FALSE.
- Blanks follow Excel: a NULL operand counts as 0 in arithmetic, as empty text in `&` and text comparisons, and as 0
  in number comparisons. AND and OR ignore blanks. A Filter sends `cond IS TRUE` to `match` and the rest to `nomatch`.
- Compiler rules: numbers are DOUBLE (`power()` for `^`); `&` compiles to `concat`; text comparison ignores case
  (`lower()` both sides); one shared number-to-text helper is used by Column mapping, `&`, TEXT and Unpivot.
- Excel results to reproduce in T1.7 to T1.9: `DATE(2026,9,31)` rolls over to 2026-10-01; `MOD(-3,2) = 1`;
  `INT(-1.5) = -2`; TRIM collapses inner runs of spaces; WEEKDAY counts Sunday as 1; FIND is case-sensitive, SEARCH is
  not and accepts wildcards; `VALUE(number)` returns the number.

## D18 Open: mixed text and number cells in an Output column (decide before T1.13 and T1.15)

The expected `Exceptions.value` column holds text (`X`) and numbers (`2`) in one column, while the compiler gives one
type per column. Do not loosen the comparison. Plan: the Output node gets a per-column opt-in that writes number-like
text as numbers, in the same spirit as the csv typing of D15 (`007` stays text). Before T1.18, dump every row of
`Exceptions` and `OT_breaches` for both expected workbooks, and check the `date` cell on `Invalid date` rows and the
`value` cell on `Missing attendance code` rows. In the flow, pin types with a Column mapping after each input, so a
blank or mixed column in one month cannot change the types of another month.

## D19 Tier 1 logic and math functions (T1.7)

- Registry: `src/engine/formula/tier1/` (`logic.ts`, `math.ts`, `index.ts`). T1.8 and T1.9 add the text and date groups.
  Functions get `ctx.arg(i, type)` (blank cell becomes 0, empty text or FALSE) or `ctx.raw(i, type)` (blank stays NULL).
- ROUND, ROUNDUP and ROUNDDOWN work on the number read at 15 significant digits as DECIMAL(38,15), because DuckDB
  `round` gives `0.285 -> 0.28` and `1.005 -> 1` where Excel gives 0.29 and 1.01. ROUNDUP and ROUNDDOWN give a blank
  for values that do not fit (above about 1e23 or below 1e-15); ROUND falls back to DOUBLE rounding there.
- CEILING and FLOOR divide at 9 digits before rounding (`1.1 / 0.1` is not 12). CEILING(x, 0) is 0, FLOOR(x, 0) is blank.
  A positive number with a negative significance is blank. FLOOR of a negative number with a positive significance
  rounds away from zero (`FLOOR(-2.5, 2) = -4`), as current Excel does.
- Known divergences from Excel, all consequences of "errors are NULL" (D17): IF with two values gives a blank when
  false (Excel gives FALSE); IFS and SWITCH give a blank when nothing matches (Excel #N/A); IFERROR also replaces a
  blank cell; ISBLANK of an error is TRUE; POWER of a negative base with a fractional exponent, SQRT of a negative
  number and MOD by zero give a blank (Excel #NUM! and #DIV/0!).
- MIN and MAX ignore blank cells and also accept dates. SUM counts a blank as 0. AND and OR ignore blanks.

## D20 Tier 1 text functions (T1.8)

- Text functions need text arguments: a number is refused with a hint to use `TEXT()`. `CONCAT`, `TEXTJOIN` and `&`
  are the exceptions and write numbers, dates and booleans with the same helper (numbers without `.0`, dates as ISO
  text, booleans as TRUE and FALSE). A blank cell is empty text.
- `LEFT`, `RIGHT` and `MID` give a blank for a negative length or a start below 1 (Excel #VALUE!). `FIND` and `SEARCH`
  give a blank when nothing is found or the start is outside the text. `SEARCH` supports `?`, `*` and `~` as Excel
  does, by building a regular expression in SQL.
- `TRIM` removes outer spaces and collapses inner runs. `PROPER` upper-cases a letter at the start or after any
  non-letter, as Excel does (`o'neil` gives `O'Neil`, `2nd` gives `2Nd`).
- `VALUE` keeps a number, reads text such as `12`, ` 2.5 `, `1,234.5`, `1e3` and `12%` (dot is the decimal mark, commas
  are thousands marks), and gives a blank for anything else, so `ISNUMBER(VALUE(x))` is the number check (rule R8).
  Dates and booleans are refused.
- `TEXT` needs its format in quotes, because it is translated when the flow is compiled. Number formats: `0`, `0.00`,
  `#,##0`, `#,##0.00`, `0%`, `0.0%`, `000` (rounding as ROUND). Date formats: yyyy, yy, mmmm, mmm, mm, m, dddd, ddd, dd, d
  with any other characters kept. Other formats are refused with the list of supported ones. Time formats and
  optional-digit decimals (`0.##`) are not supported.
