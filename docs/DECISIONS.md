# Decisions

Newest last.

## D1 Playwright uses the preinstalled Chromium (T0.1)

`@playwright/test` is pinned to 1.63.0, the version of the preinstalled `playwright`.
That version finds the bundled Chromium in `/opt/pw-browsers`, so no browser download
and no `playwright install` is needed. System Chrome is not used.

## D2 TypeScript 6.0.3, not 7 (T0.1)

`typescript-eslint` 8.73.0 accepts TypeScript `>=4.8.4 <6.1.0`. TypeScript 7 is the latest
release but would break lint, so the project pins 6.0.3. Revisit when typescript-eslint
supports 7.

## D3 Exact versions (T0.1)

`.npmrc` sets `save-exact=true` and `package-lock.json` is committed, so `npm ci` is
reproducible for `npm run gates`.

## D4 Gate scripts not built yet (T0.1)

`spike`, `test:acceptance`, `test:e2e`, `test:ui-rules` and `test:db` run
`scripts/not-implemented.mjs`, which exits 1 and names the task that replaces it.
`vitest` runs only `src/**/*.test.ts(x)`. Playwright specs live in `e2e/`.

## D5 Benchmark files count the header row (T0.2)

"1,048,576 rows" is the Excel limit including the header, so the largest files hold the
header plus 1,048,575 data rows. The other sizes use the same rule. The generator is
seeded, writes shared strings like Excel, and runs as TypeScript with Node's built-in type
stripping (`node scripts/generate-bench-files.ts`), so it needs no extra dependency.

## D6 SheetJS from its own CDN (T0.3a)

`xlsx` is installed from `https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz`, the
official install path in the SheetJS docs. 0.20.3 is the newest release on that CDN
(0.20.4 and later return 404). The npm `xlsx` package is stale and is not used.

## D7 DuckDB-WASM bundles are self-hosted (T0.3a)

The worker selects the `mvp` or `eh` bundle through Vite `?url` imports, not
`getJsDelivrBundles()`. A run therefore loads only static assets from this app, which the
no-network test in T1.20 needs. These bundles need no COOP/COEP headers.
`@duckdb/duckdb-wasm` is pinned to 1.33.1-dev57.0 (the `latest` tag) and `apache-arrow`
to 17.0.0, the version it depends on.

## D8 Spike measures a production build (T0.3a)

On a cold start the Vite dev server re-optimizes dependencies and reloads the page, which
failed one smoke run. The spike runner (T0.3b) builds the app and serves it with
`vite preview`. This also removes dev transforms from the measurements.

## D9 Own streaming xlsx reader for large files (T0.4a)

SheetJS whole-workbook parsing returns no sheet for the 500k and 1M row xlsx files (T0.3b).
`src/engine/xlsx-stream/` reads xlsx as a stream instead: zip directory by slices,
`DecompressionStream('deflate-raw')` per part, rows parsed in chunks. It adds no dependency.
Known limits, each reported with a "save as csv" message: zip64 parts and compression
methods other than stored or deflate. The 1904 date system is not handled. SheetJS stays
the reader for small files and the writer for output (T1.15).

## D10 Reading strategies chosen by the spike (T0.4b)

`docs/SPIKE_RESULTS.md` is generated by `npm run spike`, and the choice is a rule over the
numbers: the strategy that finishes at the most file sizes, then the lower total load time.
On the T0.4b run this gave `xlsx-stream` for xlsx and DuckDB `read_csv` on the file handle
for csv. SheetJS whole-workbook parsing stays only for small files and for writing output.
It returns "no sheet" without an exception for the 500k and 1M row xlsx files, and it needs
about 10 GB of renderer memory for the 1M row csv.

## D11 Size guard (T0.5)

- The limit `MAX_SAFE_XLSX_BYTES` (300,002,342) is the exact byte size of the largest xlsx that
  loaded in the spike. Files above it are refused before any parsing, with the "save as csv"
  message from `src/ui/strings.ts`. A test fails if the limit is above the largest size in
  `docs/spike-raw.json`.
- csv is not guarded. DuckDB reads it from the file handle: 378 MB took 1.1 GB of peak memory.
- Until T1.3 (input node) and T2.16 (run screen) exist, the guard is enforced only on the
  benchmark page. Both tasks now say they must call it.
- Known limit: the limit comes from a synthetic file with a pool of 2,000 distinct strings.
  A real xlsx under the limit with many distinct strings keeps its whole shared-strings table
  in memory, and this was not measured. Re-measure with real data when it is available.
- If a later spike run fails on the 1,048,576-row xlsx, `npm run check` turns red through the
  limit test. That is intended: re-measure and set the limit again. Do not loosen the test.

## D12 Flow definition envelope and ports (T1.1)

- The flow JSON follows React Flow: `nodes[{id, type, label?, position?, settings}]` and
  `edges[{source, sourceHandle?, target, targetHandle?}]`, plus `schemaVersion: 1`. Phase 2 needs no conversion.
- Ports live in one registry (`NODE_PORTS` in `src/engine/flow/types.ts`). Filter has outputs `match` and
  `nomatch`. Lookup has inputs `left` (required) and `right` (only for a lookup on another node; a reference
  table is named in the settings, never by version). Append and SQL take `in1`, `in2`, ... with no gap, and the
  number gives the order, not the position of the edge in the array. Missing handles default to the first one.
- The validator is hand-written (`src/engine/flow/validate.ts`), not `ajv`, so no dependency outside the stack
  is added. `flowJsonSchema` documents the envelope and a test keeps its node type list equal to `NODE_TYPES`.
  Settings of each node type are validated by the module of that type, task by task.
- Input nodes will bind to files by a logical key in their settings (for example "Timesheet"), not a file name,
  because file names differ per dataset.

## D13 Plan notes for the engine tasks (T1.1)

Open design points to settle in the task that needs them, each recorded here when decided:

- Row order (R12): DuckDB does not keep order through joins and group-bys. Sorting is a setting of the Output
  node (T1.15), not a separate node.
- Summary header (R10): the `*_days` and `ot_*_hours` columns follow reference table order, including zero
  columns, so Pivot (T1.13) needs a column list taken from a reference table, a fill value and a suffix.
- Input typing (R8): a mixed OT column keeps text such as `2h` as text. Type inference must not turn it into NULL.
- Identifiers are always quoted. Check whether DuckDB treats quoted names as case-insensitive and record what
  the engine enforces (CLAUDE.md wants case-sensitive column names).
- Dates leave the engine as UTC-safe values, and the acceptance spec runs with a UTC+7 time zone, so that a
  date does not move by one day.
- Fixture employee IDs must not appear in any `src/` file, tests included. The acceptance harness lives outside `src/`.

## D14 Engine core: runner, tables, column names (T1.2)

- The engine talks to DuckDB only through `SqlRunner` (`exec`, `query`, `cancel`, `close`). Two builds of the
  same DuckDB-WASM: `createNodeRunner` (Node blocking API, used by unit tests, checked to run under Vitest) and
  `createBrowserRunner` (Web Worker, used by the app). No extra dependency, no `@duckdb/node-api`.
- Every output of every node is stored as a table (`CREATE TABLE ... AS`), not a view, so a node with two
  consumers runs once. Tables carry a per-run prefix, and `dispose()` drops them.
- Node modules are synchronous: settings and input columns in, a SELECT and the exact output columns out. The
  engine tracks columns in JavaScript. This is how names stay case-sensitive: measured on DuckDB 1.5.4, a quoted
  `"a"` resolves to a column `"A"`, so `requireColumn` checks names before any SQL is built.
- Cells leave the engine as numbers (cast to DOUBLE), ISO date text (`strftime`) and text, so a date never goes
  through a JavaScript Date and cannot move by a day in another time zone.
- Cancel: the signal is checked between steps and calls `runner.cancel()`. The Node runner cannot stop a query
  that is already running; the browser runner calls `cancelSent()`.
- `TRY()` and `try_cast` exist in this DuckDB version (checked for T1.6).

## D15 Input file node (T1.3)

- Settings: `key` (logical name, one file per key, unique in a flow), `sheet`, `headerRow` (from 1, default 1),
  `skipRows` after the header, `fillDown` (column names), `rowNumberColumn` (name of an added column with the row
  number in the file; none by default). The file is read before the nodes run (`loadInputFile`); the node module only
  exposes the loaded table. `runFlow` takes `files` by key, and `inputs` for tables already in memory (tests).
- Every cell is staged as text in DuckDB and cast afterwards. xlsx column types come from the cell kinds seen while
  streaming: all numbers give number, all midnight dates give date, all booleans give boolean, anything else (mixed or
  text) stays text with numbers written as plain text. So `2h` among numbers survives (rule R8). csv columns are
  number only for plain decimals without leading zeros, date only for `YYYY-MM-DD`, otherwise text. The Column mapping
  node (T1.4) is where a user retypes a column.
- Fully blank rows are skipped. Trailing empty header cells are dropped, interior ones are named `Column N`, a
  duplicate header name is an error. For csv, `headerRow` counts non-blank lines, because DuckDB skips blank lines.
- Known limit: rows are staged with SQL INSERT in batches of 2,000. This is correct but slower than an Arrow insert.
  Throughput on a 1,000,000-row xlsx is not measured; measure it in T2.16 and switch the staging step if needed.
- Dates read from xlsx are built from UTC milliseconds, so they do not move with the time zone of the browser.

## D16 Column mapping node (T1.4)

- Settings: `columns: [{source, keep?, name?, type?}]`, one row per source column, in output order. `keep` defaults to
  true. Columns the grid does not list stay unchanged and follow the listed ones, so a flow keeps working when a file
  gains a column. Drop a column explicitly with `keep: false`.
- Conversions: any type to text (numbers without a trailing `.0`, dates as ISO text); text to number, date or boolean
  (empty text becomes NULL, a bad value fails the step and names the value); boolean to number; number to boolean
  (non-zero). Number to date and date to number are refused with a hint to use a Formula column.
- Two output names that differ only by case are refused, since one DuckDB table cannot hold both (see D14).
- `src/engine/nodes/test-helpers.ts` runs one node on in-memory tables through `runFlow`, for node unit tests.

## D17 Formula language: typing, blanks and errors (T1.6, advisor-reviewed)

- Pipeline: lexer and parser (`src/engine/formula/parse.ts`) give an AST with source positions. The compiler (T1.6b)
  turns it into DuckDB SQL plus a type (`text`, `number`, `date`, `boolean`), checked against the input columns.
  Type mismatches and non-boolean Filter conditions are compile errors with a position.
- Excel precedence: comparison, then `&`, then `+ -`, then `* /`, then `^` (left-associative: `2^3^2 = 64`), then
  unary minus (tighter than `^`: `-2^2 = 4`). Function names ignore case. Column references `[name]` do not.
- Errors are NULL, nothing throws at run time: `/` is `x / NULLIF(y, 0)`, `VALUE` and `DATE` use `TRY_CAST`.
  `IFERROR(x, alt)` is `COALESCE(x, alt)`. Two divergences from Excel, documented and not tested as Excel results:
  `IFERROR` on a bare blank reference returns `alt` (Excel gives 0), and `ISBLANK` of an error is TRUE. Use
  `ISNUMBER(VALUE(x))` to test a number, as `ISNUMBER(text)` is FALSE.
- Blanks follow Excel: a NULL operand counts as 0 in arithmetic, as empty text in `&` and text comparisons, and as 0
  in number comparisons. AND and OR ignore blanks. A Filter sends `cond IS TRUE` to `match` and the rest to `nomatch`.
- Compiler rules: numbers are DOUBLE (`power()` for `^`); `&` compiles to `concat`; text comparison ignores case
  (`lower()` both sides); one shared number-to-text helper is used by Column mapping, `&`, TEXT and Unpivot.
- Excel results to reproduce in T1.7 to T1.9: `DATE(2026,9,31)` rolls over to 2026-10-01; `MOD(-3,2) = 1`;
  `INT(-1.5) = -2`; TRIM collapses inner runs of spaces; WEEKDAY counts Sunday as 1; FIND is case-sensitive, SEARCH is
  not and accepts wildcards; `VALUE(number)` returns the number.

## D18 Open: mixed text and number cells in an Output column (decide before T1.13 and T1.15)

The expected `Exceptions.value` column holds text (`X`) and numbers (`2`) in one column, while the compiler gives one
type per column. Do not loosen the comparison. Plan: the Output node gets a per-column opt-in that writes number-like
text as numbers, in the same spirit as the csv typing of D15 (`007` stays text). Before T1.18, dump every row of
`Exceptions` and `OT_breaches` for both expected workbooks, and check the `date` cell on `Invalid date` rows and the
`value` cell on `Missing attendance code` rows. In the flow, pin types with a Column mapping after each input, so a
blank or mixed column in one month cannot change the types of another month.

## D19 Tier 1 logic and math functions (T1.7)

- Registry: `src/engine/formula/tier1/` (`logic.ts`, `math.ts`, `index.ts`). T1.8 and T1.9 add the text and date groups.
  Functions get `ctx.arg(i, type)` (blank cell becomes 0, empty text or FALSE) or `ctx.raw(i, type)` (blank stays NULL).
- ROUND, ROUNDUP and ROUNDDOWN work on the number read at 15 significant digits as DECIMAL(38,15), because DuckDB
  `round` gives `0.285 -> 0.28` and `1.005 -> 1` where Excel gives 0.29 and 1.01. ROUNDUP and ROUNDDOWN give a blank
  for values that do not fit (above about 1e23 or below 1e-15); ROUND falls back to DOUBLE rounding there.
- CEILING and FLOOR divide at 9 digits before rounding (`1.1 / 0.1` is not 12). CEILING(x, 0) is 0, FLOOR(x, 0) is blank.
  A positive number with a negative significance is blank. FLOOR of a negative number with a positive significance
  rounds away from zero (`FLOOR(-2.5, 2) = -4`), as current Excel does.
- Known divergences from Excel, all consequences of "errors are NULL" (D17): IF with two values gives a blank when
  false (Excel gives FALSE); IFS and SWITCH give a blank when nothing matches (Excel #N/A); IFERROR also replaces a
  blank cell; ISBLANK of an error is TRUE; POWER of a negative base with a fractional exponent, SQRT of a negative
  number and MOD by zero give a blank (Excel #NUM! and #DIV/0!).
- MIN and MAX ignore blank cells and also accept dates. SUM counts a blank as 0. AND and OR ignore blanks.

## D20 Tier 1 text functions (T1.8)

- Text functions need text arguments: a number is refused with a hint to use `TEXT()`. `CONCAT`, `TEXTJOIN` and `&`
  are the exceptions and write numbers, dates and booleans with the same helper (numbers without `.0`, dates as ISO
  text, booleans as TRUE and FALSE). A blank cell is empty text.
- `LEFT`, `RIGHT` and `MID` give a blank for a negative length or a start below 1 (Excel #VALUE!). `FIND` and `SEARCH`
  give a blank when nothing is found or the start is outside the text. `SEARCH` supports `?`, `*` and `~` as Excel
  does, by building a regular expression in SQL.
- `TRIM` removes outer spaces and collapses inner runs. `PROPER` upper-cases a letter at the start or after any
  non-letter, as Excel does (`o'neil` gives `O'Neil`, `2nd` gives `2Nd`).
- `VALUE` keeps a number, reads text such as `12`, ` 2.5 `, `1,234.5`, `1e3` and `12%` (dot is the decimal mark, commas
  are thousands marks), and gives a blank for anything else, so `ISNUMBER(VALUE(x))` is the number check (rule R8).
  Dates and booleans are refused.
- `TEXT` needs its format in quotes, because it is translated when the flow is compiled. Number formats: `0`, `0.00`,
  `#,##0`, `#,##0.00`, `0%`, `0.0%`, `000` (rounding as ROUND). Date formats: yyyy, yy, mmmm, mmm, mm, m, dddd, ddd, dd, d
  with any other characters kept. Other formats are refused with the list of supported ones. Time formats and
  optional-digit decimals (`0.##`) are not supported.

## D21 Tier 1 date functions (T1.9)

- `EFFECTIVE_DATE()` is the date picked for the run, as a date. A malformed effective date is a compile error.
- `DATE(y, m, d)` rolls months and days over like Excel (`DATE(2026, 9, 31)` is 2026-10-01, month 0 is December of the
  year before). A year DuckDB cannot represent gives a blank, never a failed run (`TRY`). Years below 1900 are not
  shifted by 1900 as Excel does.
- `YEAR`, `MONTH`, `DAY`, `WEEKDAY`, `WEEKNUM`, `ISOWEEKNUM`, `EOMONTH` of a blank date are blank (Excel reads a blank as
  0 January 1900). `WEEKDAY` supports return types 1, 2 and 3, `WEEKNUM` types 1, 2 and 21; other types give a blank.
- `EDATE` and `DATEDIF` use DuckDB month arithmetic, which stops at the end of a shorter month like Excel
  (`EDATE(31 Jan, 1)` is 28 Feb). `DATEDIF` needs its unit in quotes (Y, M, D, MD, YM, YD, any case); `MD` and `YD` are
  the days left after whole months or whole years, which gives Excel's result in normal cases and avoids its known bugs.
  A start after the end gives a blank.
- Date text such as "2026-09-30" is not a date. Use `DATE()` or retype the column to date in a Column mapping step.
- `src/engine/formula/tier1/coverage.test.ts` fails when the registry differs from the Tier 1 list of the spec or when
  a Tier 1 function has no call in any unit test (gate G2).

## D22 Lookup / Join node (T1.11)

- Settings: `source` (`{kind: "reference", table}` or `{kind: "node"}`, which reads the `right` input), `keys`
  (`[{left, right}]`), `bring` (`[{column, as?}]`), `onNoMatch` (`blank` default, `drop`, `fail`).
- It is a left join that keeps the left rows in their order. When the right side repeats a key, its first row wins
  (row order of the table), so left rows never multiply. This is VLOOKUP behaviour; the table is a reference table that
  people edit, so a duplicate is not an error.
- Text keys match without regard to case, as Excel lookups do; other types match exactly. A blank key never matches.
  Keys of different types are refused with a hint to use a Column mapping step. Column names are case-sensitive.
- `onNoMatch`: `blank` leaves the brought columns empty, `drop` keeps only matched rows, `fail` stops the step with
  a message such as `No match in reference table "codes" for Code = 'zz'` (DuckDB `error()`). The message shows the
  first unmatched row that the engine meets.
- A brought column whose name equals an input column, also by case only, must be renamed with `as`.
- A reference table is named, never a version. The caller (T1.16) passes the version valid on the effective date;
  a name without a version is `missing_reference_table`.

## D23 Group by node (T1.12)

- Settings: `groupBy` (column names) and `aggregations` (`[{fn, column?, as?}]`, `fn` is sum, count, min, max or
  average). `as` defaults to `sum_Hours` or `count`. The result has the group columns, then the aggregations.
- `sum` and `average` need a number column. `min` and `max` also take dates and text, and keep the type. `count` without
  a column counts rows, with a column it counts filled cells. Blanks are ignored by every function; a sum of blanks is
  0 (as Excel), an average of blanks is blank.
- Group keys match exactly, text included (unlike Lookup, which ignores case). A blank key is one group. The result is
  sorted by the group columns, blanks last, so it is deterministic. Without group columns the result is one row.
- Group columns without aggregations give a list of distinct values. A step with neither is refused.

## D24 Unpivot node (T1.13a)

- Settings: `keep` (columns that stay), `unpivot` (columns that become rows, in order), `nameColumn`, `valueColumn`,
  `skipBlank` (default false). Columns that are neither kept nor unpivoted are dropped.
- Output order is the input row order, then the order of `unpivot`. The name column holds the source column name as
  text (`1`, `2`, ...).
- The value column is always text. Numbers are written with the shared number format (8, not 8.0), dates as ISO text,
  booleans as TRUE or FALSE. Reason: the type of an unpivoted column would otherwise follow the data (all-blank day
  columns, a month with a text value), and one flow must give the same column types for every dataset. A Column
  mapping step or VALUE() turns it back into numbers. Text such as `2h` therefore stays visible to rule R8.
- Blank cells stay as rows with a blank value, because rules R6 and R8 report a missing value.

## D25 Pivot node and asynchronous compile (T1.13b)

- A node's output columns can depend on values (Pivot). `NodeModule.compile` may therefore return a promise, and its
  context has `query(sql)` to read from the tables of the run. The engine awaits it. All other nodes stay synchronous.
- Settings: `rowKeys`, `columnSource`, `value` (not needed for count), `aggregation` (sum, count, min, max, average),
  `columns` (`{from: "data"}` default, or `{from: "reference", table, column}`), `fill`, `namePrefix`, `nameSuffix`,
  `nameCase` (keep, lower, upper). A new column is named `prefix + value + suffix`, so the code `OT_DAY` with the
  suffix `_hours` and lower case gives `ot_day_hours`.
- Column list: from the data, distinct values sorted; from a reference table, its values in order of first appearance,
  each once, also when the data has no row for them (zero columns stay). With a reference list, data values that are
  not in the list are left out of the result. At most 500 columns; more is an error that says to add a Filter step.
- Rows: one per combination of row keys, sorted by the keys; without row keys one total row. Rows whose column source
  is blank are ignored.
- Missing combinations: 0 for sum, else blank, or `fill` (a number or null; only for number results). Count is always a
  number, 0 when nothing matches, and ignores `fill`. A key column clashing with a generated name (also by case) is
  refused.
- The order of the columns is the order of the list. A flow that needs another header order ends with a Column mapping
  step, which also gives the final names.

## D26 Append and SQL nodes (T1.14)

- Append: inputs `in1`, `in2`, ... in that order, each in its own row order. `match` is `name` (default) or `position`.
  By name the result has every column of every input in order of first appearance, and an input without a column
  leaves it blank. By position all inputs need the same number of columns, the first input names them. A column name
  with two types, or two names that differ only by case, is refused with a hint to use a Column mapping step.
- SQL node: the setting is `sql`, one read-only query. Inputs are called `in1`, `in2`, ... The query runs as the top
  statement of a `WITH in1 AS (...)` block (merged into the query's own WITH), so the result column names are the ones
  the user wrote. Result types: text, date, boolean and every numeric type (cast to DOUBLE, as everywhere else); any
  other type is refused with a hint to CAST it. A duplicate column name (also by case) is refused.
- Safety check (`checkSqlText`), run before the query: one statement only, starting with SELECT or WITH; words that
  write or change state (INSERT, UPDATE, DELETE, CREATE, DROP, ALTER, ATTACH, DETACH, COPY, INSTALL, LOAD, PRAGMA,
  EXPORT, IMPORT, CHECKPOINT, VACUUM); file and address readers (`read_*`, `*_scan`, `glob`, `sniff_csv`, `http_*`, a
  text value right after FROM or JOIN); and functions that run text as SQL (`query`, `query_table`). Comments, text
  values and quoted names are ignored by the check. This is best-effort defence in depth, not a sandbox: a flow can
  be shared between colleagues, and the check exists so that a shared SQL step cannot read local files, call an
  address or build SQL from data. The real guarantees are that all processing runs in the user's own browser and that
  the app sends no file content over the network (tested in T1.20).

## D27 Output node (T1.15a) and the answer to D18

- Settings: `file` (logical file name, default `Result`; steps with the same name are sheets of one workbook), `format`
  (`xlsx` default, or `csv`), `sheet` (needed for xlsx: 1 to 31 characters, none of `[ ] : * ? / \`), `sort`, `columns`,
  `numberLikeText`. `checkOutputNodes` runs at the start of every run: one format per file, one csv step per file,
  sheet names unique per workbook (ignoring case).
- `sort`: a list of `{column}` or `{expression}` (a formula) with `direction` asc (default) or desc. Blanks sort last
  in both directions, and ties keep the input order. A formula key gives an order that is not alphabetical, for
  example DAY before WEEK before MONTH (rule R12).
- `columns`: the columns written, in that order. A sort key does not need to be one of them, so helper columns do not
  reach the file.
- Observed in the expected workbooks (both datasets): dates are numeric serials with the format `yyyy-mm-dd`; blank
  cells are absent; `Exceptions.value` holds text (`X`), numbers (`2`) and text that is not a number (`2h`) in one
  column. Resolution of D18: the compiler keeps one type per column, and `numberLikeText` names text columns whose
  plain-number values (`2`, `1.5`, not `007`) the file writer (T1.15b) writes as numbers. The comparison of the
  acceptance test is not loosened.
- An Output step returns its table as the handle `result` (the engine now stores every handle a node returns), and
  `RunResult.rows()` reads all rows for the file writer.

## D28 File writer (T1.15b)

- `buildOutputFiles(result, flow)` (`src/engine/output/export.ts`) returns one file per `file` name, in order of first
  appearance: `Name.xlsx` with the sheets of its Output steps in step order, or `Name.csv`. It reads all rows of each
  Output step, not a preview. A flow without an Output step is an error that says to add one. Characters that a file
  name cannot hold become `_`.
- xlsx cells: numbers are numeric cells; dates are numeric serials computed in UTC with the format `yyyy-mm-dd`
  (never a JavaScript Date, so the time zone cannot shift them); booleans are boolean cells; text is a string cell;
  a blank value or an empty text is an absent cell. Columns listed in `numberLikeText` write plain numbers (`2`, `-1.5`,
  not `007`, not `1e3`) as numeric cells. Column widths follow the content (cosmetic).
- csv: UTF-8 with a byte order mark (so Excel reads accents), `\r\n` line ends, fields with a comma, quote or line
  break are quoted, dates as ISO text, booleans as TRUE and FALSE, blanks empty.
- The browser run screen (T2.16) turns the bytes into a download.

## D29 Effective date and version resolution (T1.16)

- `src/engine/versions.ts` holds pure functions with no data store. A version has `versionNo`, `validFrom`, `validTo`
  (null means still in effect) and `status`. Both ends of the range are included. Dates are ISO text and must be real
  calendar dates.
- `resolveVersion` returns the one version that covers the date. It never picks the nearest one. With no match it
  stops with `no_version` and a message that lists the published periods in the form `1 Jan 2026 to 31 Aug 2026` or
  `from 1 Oct 2026`, and says to pick another date or add a version. Two versions that cover one date are
  `invalid_versions` (the server forbids this too, T3.2).
- Drafts do not take effect in a run (SPEC: a published version is read-only, and a run uses what is published).
  `includeDrafts` exists for the builder's test runs in phase 2. When only a draft covers the date, the message says to
  publish it.

## D31 Timesheet flow, part 1: reading and the Exceptions sheet (T1.18)

- `flows/monthly-timesheet.flow.json` holds logic only: the logical input keys `Timesheet` and `Employees`, the layout
  of the files (sheet names, header row 3, the 31 day columns `1` to `31`), the reference table name `attendance_codes`,
  and the wording of the exception reasons and column names of the output sheet. No employee, date, count or expected
  number. The attendance codes and OT types are never named; they come from the reference table.
- Pipeline: trim the ID and read the row type; unpivot the 31 day columns to text (blanks kept); pivot the attendance
  row and the OT row of one day side by side (`raw_att`, `raw_ot`, columns from the data); day number from `VALUE`; the
  date is `DATE(year, month, day)` of the effective date, blank when the month rolled over (rule R4); employee list
  lookup (join date, leave date, and a marker for "in the list"); Filter splits unknown employees (rule R3: one row each
  through Group by) from the rest; attendance code lookup in the reference table; the day is inside the window when
  `join <= date <= leave` (blank leave date is open); one formula per row type builds the reason in the order of the
  oracle (invalid date, outside window, then the code or OT rules); a Filter keeps rows with a reason; Append joins
  the three streams; the Output step picks and orders the columns, sorts by employee, day, row type, and writes plain
  numbers of the `value` column as numbers (`numberLikeText`, D27).
- Known limits, none visible in the test data: (1) a number typed as text in an OT cell (`"2"`) counts as the number 2,
  because Unpivot writes every value as text; rule R8 would call it invalid. (2) Attendance codes match without regard
  to case (Lookup), where the oracle compares exactly. (3) An employee in the list with no join date counts as inside
  the window. (4) The pivot columns `raw_att` and `raw_ot` exist only when the file has both row types.
- While the flow is built in parts, `ACCEPTANCE_SHEETS=Exceptions npx playwright test -c playwright.acceptance.config.ts
  timesheet` compares a subset of sheets. The gate itself always compares the three sheets.
- `dist-acceptance` is ignored by ESLint (the build output of the acceptance page made `npm run check` fail once the
  page had been built).

## D32 Timesheet flow, part 2a: the OT_breaches sheet (T1.19a)

- A valid OT row is a day inside the employment window, with a known attendance code that has an OT type, and an OT
  value above 0 (rules R8 and R9). Three streams start from the valid rows:
  DAY compares the hours of the row with the `day_limit_hours` of its OT type (reference table `ot_types`); WEEK
  groups by employee and ISO week and compares with the `WEEK` row of `ot_limits`; MONTH groups by employee and
  compares with the `MONTH` row of `ot_limits`. Hours equal to a limit are not a breach (strict `>`).
- The ISO week label is `ISOYEAR-Www`, where the ISO year is the year of the Thursday of that week
  (`YEAR(date - WEEKDAY(date, 2) + 4)`), so a week that spans New Year gets the right year. All days of a run are in the
  month of the effective date, so a week only counts those days (rule R11). The month label is
  `TEXT(EFFECTIVE_DATE(), "yyyy-mm")`.
- A limit that is missing from the reference table stops the run (`onNoMatch: fail`) with a message that names the
  row, instead of counting as "no limit". The names `WEEK` and `MONTH` in the flow are the period codes of the
  reference table `ot_limits`, which the flow has to ask for.
- Sort (rule R12): employee, then the level in the order DAY, WEEK, MONTH (a formula sort key), then the period text.
- The sheet order of a workbook is the order of the Output steps in the flow file. T1.19b puts the Summary step first.

## D33 Timesheet flow, part 2b: the Summary sheet (T1.19b)

- Helper columns on the rows of known employees: `att_ok` (inside the window with a known code), `counted_category`
  (the day category of a valid row, else blank), `work_value` (work day value of a valid row, else 0),
  `ot_type_valid` and `ot_valid_hours` (OT type and hours of a valid OT row, else blank and 0). They feed the Summary and
  the three breach streams.
- Summary = Group by employee (sum of `work_value` and of `ot_valid_hours`, so every employee found in both files gets a
  row, also with no valid day) + two Pivots keyed by employee whose column lists come from the reference tables
  (`attendance_codes.day_category` and `ot_types.ot_type`, names built as lower case code plus `_days` or `_hours`) +
  Lookups that bring only the five category columns and the four OT columns that the sheet has + the counts of the
  two other sheets (Group by over the exception and breach streams), with 0 for an employee that has none. The Output
  step lists the columns in the header order of the expected sheet and sorts by employee.
- `work_days` is the sum of the work day values (half days count 0.5), not the count of WORK rows; the Pivot's own
  `work_days` count column is not brought into the sheet.
- The Summary Output step is first in the flow file, so the sheets are written as Summary, Exceptions, OT_breaches.
- Result: `npm run test:acceptance` passes for both datasets with the same flow file (see the log of T1.19b).

## D34 No network request carries file content (T1.20)

- `scripts/lib/request-audit.ts` (10 unit tests) audits the requests that a page makes. A request is allowed only if it
  is a GET to the same origin for a static asset of the built page (`/acceptance/index.html`, `/assets/<file>`,
  `/favicon.ico`), with no query, no fragment and no body. `blob:` and `data:` addresses are local and allowed. A web
  socket, another origin, another method, another path, a body, and any request that contains a marker text (plain,
  URL-encoded or base64, in the address, the headers or the body) is a violation.
- Acceptance specs: `privacy.spec.ts` runs an xlsx file and a csv file that hold marker texts, checks that the markers
  reached the output file (so the data did pass through the engine) and that the audit finds nothing; a third test
  makes a page leak on purpose (a query string, `sendBeacon`, a POST to another address) and requires the audit to
  find each, after checking that the requests before the leak were clean. `timesheet.spec.ts` audits the real timesheet
  run of both datasets, with the names of the employee list as markers.
- The csv path through `registerFileHandle` on a `File` now runs in Chromium (open item of T1.17).
- Limit: the audit sees what the page requests from the browser's network layer. It does not cover what a browser
  extension or the hosting server does with the static files.
- Worker requests: the engine runs in a Web Worker, so the audit has to see worker traffic. Checked, not assumed: the
  canary test starts a worker from a blob address that fetches `/leak-from-worker?d=<marker>`, and the audit reports it;
  and a real run's log contains the worker's `/assets/duckdb-*.wasm` request. `page.on('request')` sees both.
