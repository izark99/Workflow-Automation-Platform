# Decisions

Newest last.

## D1 Playwright uses the preinstalled Chromium (T0.1)

`@playwright/test` is pinned to 1.63.0, the version of the preinstalled `playwright`.
That version finds the bundled Chromium in `/opt/pw-browsers`, so no browser download
and no `playwright install` is needed. System Chrome is not used.

## D2 TypeScript 6.0.3, not 7 (T0.1)

`typescript-eslint` 8.73.0 accepts TypeScript `>=4.8.4 <6.1.0`. TypeScript 7 is the latest
release but would break lint, so the project pins 6.0.3. Revisit when typescript-eslint
supports 7.

## D3 Exact versions (T0.1)

`.npmrc` sets `save-exact=true` and `package-lock.json` is committed, so `npm ci` is
reproducible for `npm run gates`.

## D4 Gate scripts not built yet (T0.1)

`spike`, `test:acceptance`, `test:e2e`, `test:ui-rules` and `test:db` run
`scripts/not-implemented.mjs`, which exits 1 and names the task that replaces it.
`vitest` runs only `src/**/*.test.ts(x)`. Playwright specs live in `e2e/`.

## D5 Benchmark files count the header row (T0.2)

"1,048,576 rows" is the Excel limit including the header, so the largest files hold the
header plus 1,048,575 data rows. The other sizes use the same rule. The generator is
seeded, writes shared strings like Excel, and runs as TypeScript with Node's built-in type
stripping (`node scripts/generate-bench-files.ts`), so it needs no extra dependency.

## D6 SheetJS from its own CDN (T0.3a)

`xlsx` is installed from `https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz`, the
official install path in the SheetJS docs. 0.20.3 is the newest release on that CDN
(0.20.4 and later return 404). The npm `xlsx` package is stale and is not used.

## D7 DuckDB-WASM bundles are self-hosted (T0.3a)

The worker selects the `mvp` or `eh` bundle through Vite `?url` imports, not
`getJsDelivrBundles()`. A run therefore loads only static assets from this app, which the
no-network test in T1.20 needs. These bundles need no COOP/COEP headers.
`@duckdb/duckdb-wasm` is pinned to 1.33.1-dev57.0 (the `latest` tag) and `apache-arrow`
to 17.0.0, the version it depends on.

## D8 Spike measures a production build (T0.3a)

On a cold start the Vite dev server re-optimizes dependencies and reloads the page, which
failed one smoke run. The spike runner (T0.3b) builds the app and serves it with
`vite preview`. This also removes dev transforms from the measurements.

## D9 Own streaming xlsx reader for large files (T0.4a)

SheetJS whole-workbook parsing returns no sheet for the 500k and 1M row xlsx files (T0.3b).
`src/engine/xlsx-stream/` reads xlsx as a stream instead: zip directory by slices,
`DecompressionStream('deflate-raw')` per part, rows parsed in chunks. It adds no dependency.
Known limits, each reported with a "save as csv" message: zip64 parts and compression
methods other than stored or deflate. The 1904 date system is not handled. SheetJS stays
the reader for small files and the writer for output (T1.15).

## D10 Reading strategies chosen by the spike (T0.4b)

`docs/SPIKE_RESULTS.md` is generated by `npm run spike`, and the choice is a rule over the
numbers: the strategy that finishes at the most file sizes, then the lower total load time.
On the T0.4b run this gave `xlsx-stream` for xlsx and DuckDB `read_csv` on the file handle
for csv. SheetJS whole-workbook parsing stays only for small files and for writing output.
It returns "no sheet" without an exception for the 500k and 1M row xlsx files, and it needs
about 10 GB of renderer memory for the 1M row csv.

## D11 Size guard (T0.5)

- The limit `MAX_SAFE_XLSX_BYTES` (300,002,342) is the exact byte size of the largest xlsx that
  loaded in the spike. Files above it are refused before any parsing, with the "save as csv"
  message from `src/ui/strings.ts`. A test fails if the limit is above the largest size in
  `docs/spike-raw.json`.
- csv is not guarded. DuckDB reads it from the file handle: 378 MB took 1.1 GB of peak memory.
- Until T1.3 (input node) and T2.16 (run screen) exist, the guard is enforced only on the
  benchmark page. Both tasks now say they must call it.
- Known limit: the limit comes from a synthetic file with a pool of 2,000 distinct strings.
  A real xlsx under the limit with many distinct strings keeps its whole shared-strings table
  in memory, and this was not measured. Re-measure with real data when it is available.
- If a later spike run fails on the 1,048,576-row xlsx, `npm run check` turns red through the
  limit test. That is intended: re-measure and set the limit again. Do not loosen the test.

## D12 Flow definition envelope and ports (T1.1)

- The flow JSON follows React Flow: `nodes[{id, type, label?, position?, settings}]` and
  `edges[{source, sourceHandle?, target, targetHandle?}]`, plus `schemaVersion: 1`. Phase 2 needs no conversion.
- Ports live in one registry (`NODE_PORTS` in `src/engine/flow/types.ts`). Filter has outputs `match` and
  `nomatch`. Lookup has inputs `left` (required) and `right` (only for a lookup on another node; a reference
  table is named in the settings, never by version). Append and SQL take `in1`, `in2`, ... with no gap, and the
  number gives the order, not the position of the edge in the array. Missing handles default to the first one.
- The validator is hand-written (`src/engine/flow/validate.ts`), not `ajv`, so no dependency outside the stack
  is added. `flowJsonSchema` documents the envelope and a test keeps its node type list equal to `NODE_TYPES`.
  Settings of each node type are validated by the module of that type, task by task.
- Input nodes will bind to files by a logical key in their settings (for example "Timesheet"), not a file name,
  because file names differ per dataset.

## D13 Plan notes for the engine tasks (T1.1)

Open design points to settle in the task that needs them, each recorded here when decided:

- Row order (R12): DuckDB does not keep order through joins and group-bys. Sorting is a setting of the Output
  node (T1.15), not a separate node.
- Summary header (R10): the `*_days` and `ot_*_hours` columns follow reference table order, including zero
  columns, so Pivot (T1.13) needs a column list taken from a reference table, a fill value and a suffix.
- Input typing (R8): a mixed OT column keeps text such as `2h` as text. Type inference must not turn it into NULL.
- Identifiers are always quoted. Check whether DuckDB treats quoted names as case-insensitive and record what
  the engine enforces (CLAUDE.md wants case-sensitive column names).
- Dates leave the engine as UTC-safe values, and the acceptance spec runs with a UTC+7 time zone, so that a
  date does not move by one day.
- Fixture employee IDs must not appear in any `src/` file, tests included. The acceptance harness lives outside `src/`.

## D14 Engine core: runner, tables, column names (T1.2)

- The engine talks to DuckDB only through `SqlRunner` (`exec`, `query`, `cancel`, `close`). Two builds of the
  same DuckDB-WASM: `createNodeRunner` (Node blocking API, used by unit tests, checked to run under Vitest) and
  `createBrowserRunner` (Web Worker, used by the app). No extra dependency, no `@duckdb/node-api`.
- Every output of every node is stored as a table (`CREATE TABLE ... AS`), not a view, so a node with two
  consumers runs once. Tables carry a per-run prefix, and `dispose()` drops them.
- Node modules are synchronous: settings and input columns in, a SELECT and the exact output columns out. The
  engine tracks columns in JavaScript. This is how names stay case-sensitive: measured on DuckDB 1.5.4, a quoted
  `"a"` resolves to a column `"A"`, so `requireColumn` checks names before any SQL is built.
- Cells leave the engine as numbers (cast to DOUBLE), ISO date text (`strftime`) and text, so a date never goes
  through a JavaScript Date and cannot move by a day in another time zone.
- Cancel: the signal is checked between steps and calls `runner.cancel()`. The Node runner cannot stop a query
  that is already running; the browser runner calls `cancelSent()`.
- `TRY()` and `try_cast` exist in this DuckDB version (checked for T1.6).

## D15 Input file node (T1.3)

- Settings: `key` (logical name, one file per key, unique in a flow), `sheet`, `headerRow` (from 1, default 1),
  `skipRows` after the header, `fillDown` (column names), `rowNumberColumn` (name of an added column with the row
  number in the file; none by default). The file is read before the nodes run (`loadInputFile`); the node module only
  exposes the loaded table. `runFlow` takes `files` by key, and `inputs` for tables already in memory (tests).
- Every cell is staged as text in DuckDB and cast afterwards. xlsx column types come from the cell kinds seen while
  streaming: all numbers give number, all midnight dates give date, all booleans give boolean, anything else (mixed or
  text) stays text with numbers written as plain text. So `2h` among numbers survives (rule R8). csv columns are
  number only for plain decimals without leading zeros, date only for `YYYY-MM-DD`, otherwise text. The Column mapping
  node (T1.4) is where a user retypes a column.
- Fully blank rows are skipped. Trailing empty header cells are dropped, interior ones are named `Column N`, a
  duplicate header name is an error. For csv, `headerRow` counts non-blank lines, because DuckDB skips blank lines.
- Known limit: rows are staged with SQL INSERT in batches of 2,000. This is correct but slower than an Arrow insert.
  Throughput on a 1,000,000-row xlsx is not measured; measure it in T2.16 and switch the staging step if needed.
- Dates read from xlsx are built from UTC milliseconds, so they do not move with the time zone of the browser.

## D16 Column mapping node (T1.4)

- Settings: `columns: [{source, keep?, name?, type?}]`, one row per source column, in output order. `keep` defaults to
  true. Columns the grid does not list stay unchanged and follow the listed ones, so a flow keeps working when a file
  gains a column. Drop a column explicitly with `keep: false`.
- Conversions: any type to text (numbers without a trailing `.0`, dates as ISO text); text to number, date or boolean
  (empty text becomes NULL, a bad value fails the step and names the value); boolean to number; number to boolean
  (non-zero). Number to date and date to number are refused with a hint to use a Formula column.
- Two output names that differ only by case are refused, since one DuckDB table cannot hold both (see D14).
- `src/engine/nodes/test-helpers.ts` runs one node on in-memory tables through `runFlow`, for node unit tests.

## D17 Formula language: typing, blanks and errors (T1.6, advisor-reviewed)

- Pipeline: lexer and parser (`src/engine/formula/parse.ts`) give an AST with source positions. The compiler (T1.6b)
  turns it into DuckDB SQL plus a type (`text`, `number`, `date`, `boolean`), checked against the input columns.
  Type mismatches and non-boolean Filter conditions are compile errors with a position.
- Excel precedence: comparison, then `&`, then `+ -`, then `* /`, then `^` (left-associative: `2^3^2 = 64`), then
  unary minus (tighter than `^`: `-2^2 = 4`). Function names ignore case. Column references `[name]` do not.
- Errors are NULL, nothing throws at run time: `/` is `x / NULLIF(y, 0)`, `VALUE` and `DATE` use `TRY_CAST`.
  `IFERROR(x, alt)` is `COALESCE(x, alt)`. Two divergences from Excel, documented and not tested as Excel results:
  `IFERROR` on a bare blank reference returns `alt` (Excel gives 0), and `ISBLANK` of an error is TRUE. Use
  `ISNUMBER(VALUE(x))` to test a number, as `ISNUMBER(text)` is FALSE.
- Blanks follow Excel: a NULL operand counts as 0 in arithmetic, as empty text in `&` and text comparisons, and as 0
  in number comparisons. AND and OR ignore blanks. A Filter sends `cond IS TRUE` to `match` and the rest to `nomatch`.
- Compiler rules: numbers are DOUBLE (`power()` for `^`); `&` compiles to `concat`; text comparison ignores case
  (`lower()` both sides); one shared number-to-text helper is used by Column mapping, `&`, TEXT and Unpivot.
- Excel results to reproduce in T1.7 to T1.9: `DATE(2026,9,31)` rolls over to 2026-10-01; `MOD(-3,2) = 1`;
  `INT(-1.5) = -2`; TRIM collapses inner runs of spaces; WEEKDAY counts Sunday as 1; FIND is case-sensitive, SEARCH is
  not and accepts wildcards; `VALUE(number)` returns the number.

## D18 Open: mixed text and number cells in an Output column (decide before T1.13 and T1.15)

The expected `Exceptions.value` column holds text (`X`) and numbers (`2`) in one column, while the compiler gives one
type per column. Do not loosen the comparison. Plan: the Output node gets a per-column opt-in that writes number-like
text as numbers, in the same spirit as the csv typing of D15 (`007` stays text). Before T1.18, dump every row of
`Exceptions` and `OT_breaches` for both expected workbooks, and check the `date` cell on `Invalid date` rows and the
`value` cell on `Missing attendance code` rows. In the flow, pin types with a Column mapping after each input, so a
blank or mixed column in one month cannot change the types of another month.

## D19 Tier 1 logic and math functions (T1.7)

- Registry: `src/engine/formula/tier1/` (`logic.ts`, `math.ts`, `index.ts`). T1.8 and T1.9 add the text and date groups.
  Functions get `ctx.arg(i, type)` (blank cell becomes 0, empty text or FALSE) or `ctx.raw(i, type)` (blank stays NULL).
- ROUND, ROUNDUP and ROUNDDOWN work on the number read at 15 significant digits as DECIMAL(38,15), because DuckDB
  `round` gives `0.285 -> 0.28` and `1.005 -> 1` where Excel gives 0.29 and 1.01. ROUNDUP and ROUNDDOWN give a blank
  for values that do not fit (above about 1e23 or below 1e-15); ROUND falls back to DOUBLE rounding there.
- CEILING and FLOOR divide at 9 digits before rounding (`1.1 / 0.1` is not 12). CEILING(x, 0) is 0, FLOOR(x, 0) is blank.
  A positive number with a negative significance is blank. FLOOR of a negative number with a positive significance
  rounds away from zero (`FLOOR(-2.5, 2) = -4`), as current Excel does.
- Known divergences from Excel, all consequences of "errors are NULL" (D17): IF with two values gives a blank when
  false (Excel gives FALSE); IFS and SWITCH give a blank when nothing matches (Excel #N/A); IFERROR also replaces a
  blank cell; ISBLANK of an error is TRUE; POWER of a negative base with a fractional exponent, SQRT of a negative
  number and MOD by zero give a blank (Excel #NUM! and #DIV/0!).
- MIN and MAX ignore blank cells and also accept dates. SUM counts a blank as 0. AND and OR ignore blanks.

## D20 Tier 1 text functions (T1.8)

- Text functions need text arguments: a number is refused with a hint to use `TEXT()`. `CONCAT`, `TEXTJOIN` and `&`
  are the exceptions and write numbers, dates and booleans with the same helper (numbers without `.0`, dates as ISO
  text, booleans as TRUE and FALSE). A blank cell is empty text.
- `LEFT`, `RIGHT` and `MID` give a blank for a negative length or a start below 1 (Excel #VALUE!). `FIND` and `SEARCH`
  give a blank when nothing is found or the start is outside the text. `SEARCH` supports `?`, `*` and `~` as Excel
  does, by building a regular expression in SQL.
- `TRIM` removes outer spaces and collapses inner runs. `PROPER` upper-cases a letter at the start or after any
  non-letter, as Excel does (`o'neil` gives `O'Neil`, `2nd` gives `2Nd`).
- `VALUE` keeps a number, reads text such as `12`, ` 2.5 `, `1,234.5`, `1e3` and `12%` (dot is the decimal mark, commas
  are thousands marks), and gives a blank for anything else, so `ISNUMBER(VALUE(x))` is the number check (rule R8).
  Dates and booleans are refused.
- `TEXT` needs its format in quotes, because it is translated when the flow is compiled. Number formats: `0`, `0.00`,
  `#,##0`, `#,##0.00`, `0%`, `0.0%`, `000` (rounding as ROUND). Date formats: yyyy, yy, mmmm, mmm, mm, m, dddd, ddd, dd, d
  with any other characters kept. Other formats are refused with the list of supported ones. Time formats and
  optional-digit decimals (`0.##`) are not supported.

## D21 Tier 1 date functions (T1.9)

- `EFFECTIVE_DATE()` is the date picked for the run, as a date. A malformed effective date is a compile error.
- `DATE(y, m, d)` rolls months and days over like Excel (`DATE(2026, 9, 31)` is 2026-10-01, month 0 is December of the
  year before). A year DuckDB cannot represent gives a blank, never a failed run (`TRY`). Years below 1900 are not
  shifted by 1900 as Excel does.
- `YEAR`, `MONTH`, `DAY`, `WEEKDAY`, `WEEKNUM`, `ISOWEEKNUM`, `EOMONTH` of a blank date are blank (Excel reads a blank as
  0 January 1900). `WEEKDAY` supports return types 1, 2 and 3, `WEEKNUM` types 1, 2 and 21; other types give a blank.
- `EDATE` and `DATEDIF` use DuckDB month arithmetic, which stops at the end of a shorter month like Excel
  (`EDATE(31 Jan, 1)` is 28 Feb). `DATEDIF` needs its unit in quotes (Y, M, D, MD, YM, YD, any case); `MD` and `YD` are
  the days left after whole months or whole years, which gives Excel's result in normal cases and avoids its known bugs.
  A start after the end gives a blank.
- Date text such as "2026-09-30" is not a date. Use `DATE()` or retype the column to date in a Column mapping step.
- `src/engine/formula/tier1/coverage.test.ts` fails when the registry differs from the Tier 1 list of the spec or when
  a Tier 1 function has no call in any unit test (gate G2).

## D22 Lookup / Join node (T1.11)

- Settings: `source` (`{kind: "reference", table}` or `{kind: "node"}`, which reads the `right` input), `keys`
  (`[{left, right}]`), `bring` (`[{column, as?}]`), `onNoMatch` (`blank` default, `drop`, `fail`).
- It is a left join that keeps the left rows in their order. When the right side repeats a key, its first row wins
  (row order of the table), so left rows never multiply. This is VLOOKUP behaviour; the table is a reference table that
  people edit, so a duplicate is not an error.
- Text keys match without regard to case, as Excel lookups do; other types match exactly. A blank key never matches.
  Keys of different types are refused with a hint to use a Column mapping step. Column names are case-sensitive.
- `onNoMatch`: `blank` leaves the brought columns empty, `drop` keeps only matched rows, `fail` stops the step with
  a message such as `No match in reference table "codes" for Code = 'zz'` (DuckDB `error()`). The message shows the
  first unmatched row that the engine meets.
- A brought column whose name equals an input column, also by case only, must be renamed with `as`.
- A reference table is named, never a version. The caller (T1.16) passes the version valid on the effective date;
  a name without a version is `missing_reference_table`.

## D23 Group by node (T1.12)

- Settings: `groupBy` (column names) and `aggregations` (`[{fn, column?, as?}]`, `fn` is sum, count, min, max or
  average). `as` defaults to `sum_Hours` or `count`. The result has the group columns, then the aggregations.
- `sum` and `average` need a number column. `min` and `max` also take dates and text, and keep the type. `count` without
  a column counts rows, with a column it counts filled cells. Blanks are ignored by every function; a sum of blanks is
  0 (as Excel), an average of blanks is blank.
- Group keys match exactly, text included (unlike Lookup, which ignores case). A blank key is one group. The result is
  sorted by the group columns, blanks last, so it is deterministic. Without group columns the result is one row.
- Group columns without aggregations give a list of distinct values. A step with neither is refused.

## D24 Unpivot node (T1.13a)

- Settings: `keep` (columns that stay), `unpivot` (columns that become rows, in order), `nameColumn`, `valueColumn`,
  `skipBlank` (default false). Columns that are neither kept nor unpivoted are dropped.
- Output order is the input row order, then the order of `unpivot`. The name column holds the source column name as
  text (`1`, `2`, ...).
- The value column is always text. Numbers are written with the shared number format (8, not 8.0), dates as ISO text,
  booleans as TRUE or FALSE. Reason: the type of an unpivoted column would otherwise follow the data (all-blank day
  columns, a month with a text value), and one flow must give the same column types for every dataset. A Column
  mapping step or VALUE() turns it back into numbers. Text such as `2h` therefore stays visible to rule R8.
- Blank cells stay as rows with a blank value, because rules R6 and R8 report a missing value.

## D25 Pivot node and asynchronous compile (T1.13b)

- A node's output columns can depend on values (Pivot). `NodeModule.compile` may therefore return a promise, and its
  context has `query(sql)` to read from the tables of the run. The engine awaits it. All other nodes stay synchronous.
- Settings: `rowKeys`, `columnSource`, `value` (not needed for count), `aggregation` (sum, count, min, max, average),
  `columns` (`{from: "data"}` default, or `{from: "reference", table, column}`), `fill`, `namePrefix`, `nameSuffix`,
  `nameCase` (keep, lower, upper). A new column is named `prefix + value + suffix`, so the code `OT_DAY` with the
  suffix `_hours` and lower case gives `ot_day_hours`.
- Column list: from the data, distinct values sorted; from a reference table, its values in order of first appearance,
  each once, also when the data has no row for them (zero columns stay). With a reference list, data values that are
  not in the list are left out of the result. At most 500 columns; more is an error that says to add a Filter step.
- Rows: one per combination of row keys, sorted by the keys; without row keys one total row. Rows whose column source
  is blank are ignored.
- Missing combinations: 0 for sum, else blank, or `fill` (a number or null; only for number results). Count is always a
  number, 0 when nothing matches, and ignores `fill`. A key column clashing with a generated name (also by case) is
  refused.
- The order of the columns is the order of the list. A flow that needs another header order ends with a Column mapping
  step, which also gives the final names.

## D26 Append and SQL nodes (T1.14)

- Append: inputs `in1`, `in2`, ... in that order, each in its own row order. `match` is `name` (default) or `position`.
  By name the result has every column of every input in order of first appearance, and an input without a column
  leaves it blank. By position all inputs need the same number of columns, the first input names them. A column name
  with two types, or two names that differ only by case, is refused with a hint to use a Column mapping step.
- SQL node: the setting is `sql`, one read-only query. Inputs are called `in1`, `in2`, ... The query runs as the top
  statement of a `WITH in1 AS (...)` block (merged into the query's own WITH), so the result column names are the ones
  the user wrote. Result types: text, date, boolean and every numeric type (cast to DOUBLE, as everywhere else); any
  other type is refused with a hint to CAST it. A duplicate column name (also by case) is refused.
- Safety check (`checkSqlText`), run before the query: one statement only, starting with SELECT or WITH; words that
  write or change state (INSERT, UPDATE, DELETE, CREATE, DROP, ALTER, ATTACH, DETACH, COPY, INSTALL, LOAD, PRAGMA,
  EXPORT, IMPORT, CHECKPOINT, VACUUM); file and address readers (`read_*`, `*_scan`, `glob`, `sniff_csv`, `http_*`, a
  text value right after FROM or JOIN); and functions that run text as SQL (`query`, `query_table`). Comments, text
  values and quoted names are ignored by the check. This is best-effort defence in depth, not a sandbox: a flow can
  be shared between colleagues, and the check exists so that a shared SQL step cannot read local files, call an
  address or build SQL from data. The real guarantees are that all processing runs in the user's own browser and that
  the app sends no file content over the network (tested in T1.20).

## D27 Output node (T1.15a) and the answer to D18

- Settings: `file` (logical file name, default `Result`; steps with the same name are sheets of one workbook), `format`
  (`xlsx` default, or `csv`), `sheet` (needed for xlsx: 1 to 31 characters, none of `[ ] : * ? / \`), `sort`, `columns`,
  `numberLikeText`. `checkOutputNodes` runs at the start of every run: one format per file, one csv step per file,
  sheet names unique per workbook (ignoring case).
- `sort`: a list of `{column}` or `{expression}` (a formula) with `direction` asc (default) or desc. Blanks sort last
  in both directions, and ties keep the input order. A formula key gives an order that is not alphabetical, for
  example DAY before WEEK before MONTH (rule R12).
- `columns`: the columns written, in that order. A sort key does not need to be one of them, so helper columns do not
  reach the file.
- Observed in the expected workbooks (both datasets): dates are numeric serials with the format `yyyy-mm-dd`; blank
  cells are absent; `Exceptions.value` holds text (`X`), numbers (`2`) and text that is not a number (`2h`) in one
  column. Resolution of D18: the compiler keeps one type per column, and `numberLikeText` names text columns whose
  plain-number values (`2`, `1.5`, not `007`) the file writer (T1.15b) writes as numbers. The comparison of the
  acceptance test is not loosened.
- An Output step returns its table as the handle `result` (the engine now stores every handle a node returns), and
  `RunResult.rows()` reads all rows for the file writer.

## D28 File writer (T1.15b)

- `buildOutputFiles(result, flow)` (`src/engine/output/export.ts`) returns one file per `file` name, in order of first
  appearance: `Name.xlsx` with the sheets of its Output steps in step order, or `Name.csv`. It reads all rows of each
  Output step, not a preview. A flow without an Output step is an error that says to add one. Characters that a file
  name cannot hold become `_`.
- xlsx cells: numbers are numeric cells; dates are numeric serials computed in UTC with the format `yyyy-mm-dd`
  (never a JavaScript Date, so the time zone cannot shift them); booleans are boolean cells; text is a string cell;
  a blank value or an empty text is an absent cell. Columns listed in `numberLikeText` write plain numbers (`2`, `-1.5`,
  not `007`, not `1e3`) as numeric cells. Column widths follow the content (cosmetic).
- csv: UTF-8 with a byte order mark (so Excel reads accents), `\r\n` line ends, fields with a comma, quote or line
  break are quoted, dates as ISO text, booleans as TRUE and FALSE, blanks empty.
- The browser run screen (T2.16) turns the bytes into a download.

## D29 Effective date and version resolution (T1.16)

- `src/engine/versions.ts` holds pure functions with no data store. A version has `versionNo`, `validFrom`, `validTo`
  (null means still in effect) and `status`. Both ends of the range are included. Dates are ISO text and must be real
  calendar dates.
- `resolveVersion` returns the one version that covers the date. It never picks the nearest one. With no match it
  stops with `no_version` and a message that lists the published periods in the form `1 Jan 2026 to 31 Aug 2026` or
  `from 1 Oct 2026`, and says to pick another date or add a version. Two versions that cover one date are
  `invalid_versions` (the server forbids this too, T3.2).
- Drafts do not take effect in a run (SPEC: a published version is read-only, and a run uses what is published).
  `includeDrafts` exists for the builder's test runs in phase 2. When only a draft covers the date, the message says to
  publish it.

## D31 Timesheet flow, part 1: reading and the Exceptions sheet (T1.18)

- `flows/monthly-timesheet.flow.json` holds logic only: the logical input keys `Timesheet` and `Employees`, the layout
  of the files (sheet names, header row 3, the 31 day columns `1` to `31`), the reference table name `attendance_codes`,
  and the wording of the exception reasons and column names of the output sheet. No employee, date, count or expected
  number. The attendance codes and OT types are never named; they come from the reference table.
- Pipeline: trim the ID and read the row type; unpivot the 31 day columns to text (blanks kept); pivot the attendance
  row and the OT row of one day side by side (`raw_att`, `raw_ot`, columns from the data); day number from `VALUE`; the
  date is `DATE(year, month, day)` of the effective date, blank when the month rolled over (rule R4); employee list
  lookup (join date, leave date, and a marker for "in the list"); Filter splits unknown employees (rule R3: one row each
  through Group by) from the rest; attendance code lookup in the reference table; the day is inside the window when
  `join <= date <= leave` (blank leave date is open); one formula per row type builds the reason in the order of the
  oracle (invalid date, outside window, then the code or OT rules); a Filter keeps rows with a reason; Append joins
  the three streams; the Output step picks and orders the columns, sorts by employee, day, row type, and writes plain
  numbers of the `value` column as numbers (`numberLikeText`, D27).
- Known limits, none visible in the test data: (1) a number typed as text in an OT cell (`"2"`) counts as the number 2,
  because Unpivot writes every value as text; rule R8 would call it invalid. (2) Attendance codes match without regard
  to case (Lookup), where the oracle compares exactly. (3) An employee in the list with no join date counts as inside
  the window. (4) The pivot columns `raw_att` and `raw_ot` exist only when the file has both row types.
- While the flow is built in parts, `ACCEPTANCE_SHEETS=Exceptions npx playwright test -c playwright.acceptance.config.ts
  timesheet` compares a subset of sheets. The gate itself always compares the three sheets.
- `dist-acceptance` is ignored by ESLint (the build output of the acceptance page made `npm run check` fail once the
  page had been built).

## D32 Timesheet flow, part 2a: the OT_breaches sheet (T1.19a)

- A valid OT row is a day inside the employment window, with a known attendance code that has an OT type, and an OT
  value above 0 (rules R8 and R9). Three streams start from the valid rows:
  DAY compares the hours of the row with the `day_limit_hours` of its OT type (reference table `ot_types`); WEEK
  groups by employee and ISO week and compares with the `WEEK` row of `ot_limits`; MONTH groups by employee and
  compares with the `MONTH` row of `ot_limits`. Hours equal to a limit are not a breach (strict `>`).
- The ISO week label is `ISOYEAR-Www`, where the ISO year is the year of the Thursday of that week
  (`YEAR(date - WEEKDAY(date, 2) + 4)`), so a week that spans New Year gets the right year. All days of a run are in the
  month of the effective date, so a week only counts those days (rule R11). The month label is
  `TEXT(EFFECTIVE_DATE(), "yyyy-mm")`.
- A limit that is missing from the reference table stops the run (`onNoMatch: fail`) with a message that names the
  row, instead of counting as "no limit". The names `WEEK` and `MONTH` in the flow are the period codes of the
  reference table `ot_limits`, which the flow has to ask for.
- Sort (rule R12): employee, then the level in the order DAY, WEEK, MONTH (a formula sort key), then the period text.
- The sheet order of a workbook is the order of the Output steps in the flow file. T1.19b puts the Summary step first.

## D33 Timesheet flow, part 2b: the Summary sheet (T1.19b)

- Helper columns on the rows of known employees: `att_ok` (inside the window with a known code), `counted_category`
  (the day category of a valid row, else blank), `work_value` (work day value of a valid row, else 0),
  `ot_type_valid` and `ot_valid_hours` (OT type and hours of a valid OT row, else blank and 0). They feed the Summary and
  the three breach streams.
- Summary = Group by employee (sum of `work_value` and of `ot_valid_hours`, so every employee found in both files gets a
  row, also with no valid day) + two Pivots keyed by employee whose column lists come from the reference tables
  (`attendance_codes.day_category` and `ot_types.ot_type`, names built as lower case code plus `_days` or `_hours`) +
  Lookups that bring only the five category columns and the four OT columns that the sheet has + the counts of the
  two other sheets (Group by over the exception and breach streams), with 0 for an employee that has none. The Output
  step lists the columns in the header order of the expected sheet and sorts by employee.
- `work_days` is the sum of the work day values (half days count 0.5), not the count of WORK rows; the Pivot's own
  `work_days` count column is not brought into the sheet.
- The Summary Output step is first in the flow file, so the sheets are written as Summary, Exceptions, OT_breaches.
- Result: `npm run test:acceptance` passes for both datasets with the same flow file (see the log of T1.19b).

## D34 No network request carries file content (T1.20)

- `scripts/lib/request-audit.ts` (10 unit tests) audits the requests that a page makes. A request is allowed only if it

  socket, another origin, another method, another path, a body, and any request that contains a marker text (plain,

  reached the output file (so the data did pass through the engine) and that the audit finds nothing; a third test

  find each, after checking that the requests before the leak were clean. `timesheet.spec.ts` audits the real timesheet
  run of both datasets, with the names of the employee list as markers.
- The csv path through `registerFileHandle` on a `File` now runs in Chromium (open item of T1.17).
- Limit: the audit sees what the page requests from the browser's network layer. It does not cover what a browser
  extension or the hosting server does with the static files.
- Worker requests: the engine runs in a Web Worker, so the audit has to see worker traffic. Checked, not assumed: the
  canary test starts a worker from a blob address that fetches `/leak-from-worker?d=<marker>`, and the audit reports it;

Only complete rows are written (a key pair needs both columns, a brought column needs its name); the form says in words what is still missing ("Still missing: ..." or "The lookup is complete") instead of blocking edits.
- Group by: group columns (chips) and aggregations (function, column, result name). A count may have no column; any other function needs one. The result name is written only when it differs from the engine's default (`sum_hours`, `count`). Incomplete aggregations stay in the form but are not written.
- New steps start with the empty valid shape (`source: node, keys: [], bring: [], onNoMatch: blank`; `groupBy: [], aggregations: []`), so the engine's own message ("needs at least one pair of key columns") appears in the preview until the form is complete.
- Browser tests check the forms by effect on a real preview: a reference-table lookup brings 16 and 40 and leaves a blank for no match; "drop" removes the row; "stop" names the missing key (YEAR); a group-by gives sum and count per department; a sum of a text column gives the engine's message.

## D46 Unpivot and Pivot forms (T2.13b)

- Unpivot form: two column lists (keep, unpivot), the names of the name column and value column, and "Skip rows whose value is blank". A new step starts with the names `name` and `value` and empty lists. A column is in one list only: adding it to a list when it is in the other one is refused with "X is already in the columns to keep. Remove it there first", and the list stays; with the columns loaded, the dropdown of a list does not offer the columns of the other list. With the columns loaded, "Unpivot all other columns" fills the unpivot list with every column that is not kept (the day columns of a timesheet). The form says what is still missing (a column to unpivot, the two names, different names).
- Pivot form: row keys (list), the column whose values become columns, the value column (not needed for count), the aggregation, where the new columns come from (the values found in the data, sorted; or a reference table and one of its columns, in the table's order and with values that have no data), the fill value, name prefix and suffix, and the letter case. Only what differs from the engine's default is written (no fill, no prefix, no suffix, case "as in the data").
- Fill value: empty means the engine default (0 for sum, blank for the others); a number sets it; the word `blank` means a blank (null). Anything else shows "X is not a number. Type a number, the word blank, or leave the field empty." and the previous setting stays.
- The letter case changes the values that become names; the prefix and suffix stay as typed (engine rule D25). The label and a hint say so; the first e2e expectation of mine (upper case prefix and suffix) was wrong and the engine was right.
- The columns of a reference table come from its newest version (as in D45). The e2e test checks the list in reference-table order with a value that has no data (OT_NIGHT and OT_HOLIDAY get 0).

## D47 Append, Output and SQL forms (T2.14); every step type has a form

## D57 Version constraints in the database (T3.2)

- No overlap: an exclusion constraint on `daterange(valid_from, valid_to, '[]')` per flow and per reference table (extension `btree_gist`), partial on `status = 'published'`. An empty `valid_to` is an open end. Drafts may overlap, as in the local store.
- Read-only: a trigger refuses any update of a published version and any direct delete, for every role, the admin included. A delete that comes from a cascade (purge of a flow or table, T3.5) is allowed: it is told apart by the trigger depth.
- The one allowed change is rule 6, closing the previous open-ended version. The publish functions `publish_flow_version` and `publish_ref_table_version` do it in one call: set `valid_to` of the previous open-ended version to the day before, then set the draft to published, so the exclusion constraint never sees both. They set the transaction setting `app.closing_version` for that update; the trigger accepts a change of `valid_to` from null only while it is set. The API only exposes functions, so a client cannot set it.
- The functions are security invoker, so the policies of T3.3 and T3.4 decide who may call them.
- Row cap: check `jsonb_array_length(rows) <= 50000`.
- Errors say what failed and what to do next ("Create a new version copied from it", "Publish a new version instead").

## D58 Row-level security model for flows (T3.3)

- Four helper functions, all `security definer` with an empty `search_path` so that a policy can read `profiles`, `flows` and `group_members` without hitting the policies of those tables: `is_admin()`, `can_view_flow(id)`, `can_edit_flow(id)`, `is_group_member(group_id)`. Execute is granted to `authenticated` only.
- `can_view_flow`: the admin (deleted flows too), the owner of a live personal flow, a member of a group that has access to a live shared flow. `can_edit_flow`: the admin, or the owner of a live personal flow. A member of a group never changes a shared flow.
- `flows`: select by `can_view_flow`; insert and update need the admin, or `owner_id = auth.uid()` and `scope = 'personal'` (so a user can neither create a shared flow, nor make one shared, nor hand a flow to someone else); a user deletes softly by setting `deleted_at`; a delete for good is for the admin. A trigger refuses to clear `deleted_at` unless `is_admin()`, so a restore is admin-only even if a policy changes later.
- `flow_versions` follow the flow: visible to whoever can view the flow (drafts included, the spec is silent), changed by whoever can edit it. A user copies a shared flow by inserting a personal flow and selecting the definition from the shared version, which the policies allow. The publish functions are security invoker, so the same rights apply; a caller without edit rights gets "does not exist, or you may not change it".
- `flow_group_access`: admin writes; a member sees the rows of the groups they belong to.
- Policies grant to `authenticated` only; `anon` has none and so sees nothing.
- Tests (`030-rls-flows.test.sql`) act as the admin, an owner, a group member and another user through `set local role` and `request.jwt.claims`. A mutation check (delete policy `true`, view helper `true`) fails 13 of them.

## D59 Row-level security for reference tables, profiles, groups and the run log (T3.4)

- Reference tables and their versions: every signed-in user reads all (drafts included); only the admin writes. Published versions stay read-only for the admin too (D57). The publish function checks rights through the policies.
- Profiles: a user reads the own row only (the app needs the own role and name); the admin reads and manages all. A user cannot update the own row, so nobody can make themselves admin. The SPEC says users and groups are "no access" for non-admins; the own profile row is the one exception, because sign-in (T3.7) needs it. Profile rows are created by the admin; a trigger that creates one when a user signs up is left to T3.7.
- Groups and group members: admin only, so a member cannot read groups or add themselves to one. A member's own group membership reaches the policies through the definer helper `is_group_member` (D58), not through a read of the table.
- Run log: append only. A user inserts a row as themselves (`user_id = auth.uid()`) for a flow they can view; they read their own rows; the admin reads all. There is no update or delete policy; rows leave with their flow by cascade.
- `anon` has no table privileges (revoked, and removed from the default privileges of `public`), so a signed-out request fails with a permission error even before the policies.
- Tests (`040-rls-other-tables.test.sql`) use the four personas plus `anon`. A mutation check (profiles, group members and the run log insert opened up) fails the tests.

## D60 Soft delete, restore and removal after 30 days (T3.5)

- Four functions, security invoker, so the policies of T3.3 decide who may call them: `delete_flow` (a user for a personal flow, the admin for any flow; sets `deleted_at`), `restore_flow` (admin), `purge_flow` (admin, a deleted flow only), `purge_expired_flows` (removes every flow with `deleted_at <= now() - 30 days`, returns the count). A call that changes nothing raises SQLSTATE P0002 with a message that says what to do ("not in the deleted list, or only an admin can restore it"); the database does not tell a user whether a flow they cannot see exists.
- The 30 days match `purgeExpired` in the local store: a flow stays while `deleted_at` is later than now minus 30 days, so it goes at exactly 30 days. A test pins the boundary (30 days goes, 29 days 23 hours 59 minutes stays; changing `<=` to `<` fails four tests).
- Removal is a delete of the flow row; versions, group access and run log rows follow by cascade. The published-version guard allows this (D57).
- Who triggers the removal: the Admin screen, when it opens (as the local store does), and the daily keep-alive of T3.8 with the service role, which bypasses row-level security. No database scheduler (pg_cron) is used, so the local stack needs no extra extension.
- Hiding a deleted flow is done by `can_view_flow` (D58); restore stays admin-only through the trigger of T3.3.
- Execute on these functions and on the publish functions is granted to `authenticated` and `service_role`, not to `anon`.

## D61 SupabaseStore, read side (T3.6a)

- `@supabase/supabase-js` 2.118.0 is pinned. It is the client of the Supabase part of the fixed stack, not an extra dependency.
- `SupabaseStore` takes a client in its constructor, so tests and the app decide how it is made. It is not selected by the app yet (T3.6c does that); the write methods throw a StoreError that says they are not available on the server yet (T3.6b).
- Row mapping is in `supabase-mapping.ts`: pure functions from snake_case rows to the store records, with unit tests. Versions are sorted by number; group ids by group name.
- Database errors become StoreErrors in one place (`storeErrorFrom`): 42501 is forbidden, 23P01 (overlap) and 23505 are conflict, 23514 is invalid, P0002 and PGRST116 are not_found; a rule the database raised itself (P0001, P0002) keeps its own message, which already says what to do.
- What a non-admin cannot read, by D59, shows as follows: `currentUser().groupIds` is empty (only the Admin screen uses it); `ownerName` of a flow owned by someone else is "Unknown" and `groupNames` is empty. T3.6c checks against the real stack whether the Flows list needs the owner's name for non-admins and, if it does, adds a small security-definer function for it.
- The read methods are verified against the real local stack in T3.6c, not with a fake client: a fake of the query builder would only test the fake.

## D62 Server functions for the write side (T3.6b1)

- Seven security-invoker functions, so the policies of T3.3 and T3.4 still decide who may act: `create_flow`, `copy_flow`, `create_flow_version`, `create_ref_table`, `create_ref_table_version`, `set_flow_groups`, `set_user_groups`. Reasons: a flow and its first version must be written together; "the next version number" must be taken inside the database under a row lock (two callers cannot get the same number); replacing a list of groups must not leave half a list.
- A new flow or reference table gets its id from `gen_random_uuid()` first and is inserted without RETURNING. With RETURNING, the select policy runs `can_view_flow` on the new row, and a stable function cannot see a row inserted by its own statement, so the insert is refused. A mutation that uses RETURNING fails the tests with exactly that error.
- Defaults match the local store: a new flow has an empty draft version 1 starting today with the note "First version"; a copy has one draft starting at the latest version's start day, with the note "Copied from <name>" and the latest definition; the name is trimmed; a blank name is refused.
- `set_flow_groups` and `set_user_groups` check `is_admin()` first and raise 42501, so a non-admin is refused even when the list is empty (without the check an empty list would delete nothing and look like success). Unknown group ids are dropped; a repeated id is stored once.
- The last admin cannot be demoted or removed (trigger on `profiles`), as in the local store. A cascade from the Auth user is blocked the same way.
- Error codes the client maps (T3.6b2): 22023 (invalid input, message written for the user), P0002 (not found or not allowed), P0001 (a rule), 42501 (forbidden).
- Not done here: adding a user. A profile belongs to an Auth user, which only the Auth service can create; T3.7 decides how the first profile and invited users appear.

## D63 SupabaseStore, write side (T3.6b2)

- Every write goes through a database function where it touches more than one row or needs a number from the database (D62, T3.2, T3.5): create, copy, new versions, group lists, publish, delete, restore, purge. Single-row writes use a table update with only the fields of the patch (`versionPatchToRow`, `refPatchToRow`): saving a version, a user's profile, a group name, a run log row.
- Before writing, the store runs the same checks as `LocalStore`, so a person reads the same message on both: `checkRange` and `checkRowCap` (moved to `src/store/checks.ts`, now also used by `LocalStore`), the rule that a published version is read-only, the "view and run only" message for a shared flow, and `planPublish` (names the version a publish would overlap). The database enforces all of it again; the client checks are for the message, not for safety.
- An update that matches no row (row-level security hid it, or it is gone) says "You cannot change ..., or it no longer exists. Reload the page and try again."
- `storeErrorFrom` now also maps the overlap (23P01) to a sentence with what to do, a duplicate (23505) to "that name or email is already used", and keeps the database's own message for 22023.
- Adding a user is not possible from the client: a profile belongs to an Auth user, which only the Auth service creates. `saveUser` without an id says that a new user must sign in once first. T3.7 settles how the first profile and later profiles appear.
- Verified for real in T3.6c against the full local stack; here the pure parts (mappers, checks, error mapping) are unit-tested and the app gates were rerun because `local-store.ts` changed.

## D66 A profile for every Auth user (T3.7a)

- A trigger on `auth.users` (`handle_new_user`, security definer) creates the profile: name from the `name` in the user's metadata (trimmed), else the part of the email before the `@`; email as given; role always `user`. The metadata of a user is editable by that user at sign-up, so a role in it is ignored; a test with `"role":"admin"` in both metadata fields proves it, and a mutation that reads the role from the metadata fails that test.

- The existing database tests insert the profile of each fixture user; with the trigger they now upsert it (`on conflict (id) do update`), so a fixture user is created in `auth.users` and its profile is set to the wanted name and role.

## D67 Sign-in service, separate from the data (T3.7b1)

- `AuthService` (`src/store/auth.ts`): `getSession`, `signIn`, `signOut`, `onChange`. Events are `signed_in`, `signed_out` (the person asked) and `session_ended` (it ended by itself: expired, revoked, or signed out in another tab). The gate of T3.7b2 shows "Your session ended" only for the last one.
- `SupabaseAuth` uses the same client as `SupabaseStore`, so one sign-in is one session for both. It tells `signed_out` from `session_ended` by a flag that is set while its own `signOut` runs. It never calls the client from inside the state callback (a documented deadlock risk). `SIGNED_IN` repeats when a tab regains focus; the gate compares the user, so it does not remount the app.
- Sign-in problems read the same for a wrong password and an unknown email ("The email or the password is wrong"), so the screen does not reveal which emails have accounts. Other messages: unconfirmed email, rate limit, lost connection, anything else with the server's text; every one says what to do next. The form is checked first (`signInProblem`) for an empty or malformed email and an empty password.
- `MemoryAuth` is the stand-in for the local build and for tests: accounts come from the dev key `dfw.auth` (dev and test builds only, like `dfw.seed` in D37), the session is kept in localStorage so a reload restores it, and `window.dfwAuth.expire()` ends it. Its passwords are plain text, because it protects nothing: it only lets the e2e and UI-rules builds, which have no server, show and test the sign-in screen. The real service is tested by `integration/supabase-auth.test.ts` against the local Auth container (`npm run test:store`).
- `createBackend()` returns `{ store, auth }`: Supabase for both when the two variables are set; otherwise the local store with `auth: null`, or with a `MemoryAuth` when `dfw.auth` is set in a dev or test build. `createDataStore()` stays and returns only the store; the app switches to `createBackend()` in T3.7b2.
- Not in scope: sign-up, password reset, magic links. The admin creates accounts in Supabase Auth (D66); a person who forgets the password asks the admin, who resets it there. Recorded as a limit in docs/DEPLOY.md (T3.9).

Sign in again to continue." shows only when the service reports a session that ended by itself, never after the person chose to sign out.

## D69 Daily keep-alive (T3.8)

- A free Supabase project pauses after a week without requests. `public.keep_alive()` (security definer, read only, no input) reads one row of `profiles` and returns `now()`. It may be called with the public anon key, returns no table data, and changes nothing; a pgTAP test shows that `anon` gets the time and still cannot read a table.
- `scripts/keep-alive.ts` calls it through the REST API (`/rest/v1/rpc/keep_alive`) with `SUPABASE_URL` and `SUPABASE_ANON_KEY`. With `SUPABASE_SERVICE_KEY` it also calls `purge_expired_flows()`, so the removal after 30 days (D60) happens without an admin opening the screen. That removal stays out of the anon function on purpose: an endpoint that anyone can call should not delete data.
- A server error or a lost connection is retried twice (2 s, 4 s); a refused request (401, 404) fails at once with the cause. The keys are never logged or put in an error (a test checks it). The script is TypeScript with type annotations only, which Node 22 runs without a build step.
- `.github/workflows/keep-alive.yml` runs it every day at 03:17 UTC and by hand (`workflow_dispatch`), with `contents: read` only and the keys from repository secrets. It is code and instructions: nothing in this repository runs it, and nothing was deployed. GitHub pauses scheduled workflows after 60 days without repository activity; `docs/KEEP_ALIVE.md` says so and names a Cloudflare cron trigger as an alternative.
- The script is covered by 7 unit tests (fake fetch) and by `integration/keep-alive.test.ts` against the real local stack: the anon call, the purge with the service key (a flow deleted 31 days ago goes, one deleted 5 days ago stays), and a wrong key.

## D71 The Pages build loads DuckDB-WASM from jsDelivr (owner's choice, after T3.9)

## D72 Message catalog design (Phase 4, T4.7a1)

- Keys are flat and dotted, declared `as const` in `src/ui/i18n/messages/en.ts`; `MessageKey` is derived from them. The first segment is the screen and comes from the fixed list `KEY_PREFIXES` (a unit test checks it). The Texts tab filters by that prefix (T4.7g) and `ui_texts` stores `(key, locale, value)` directly.
- A text never holds a function. Dynamic values are `{name}` placeholders, formatted by the caller and passed as strings. Plural forms use `{count, plural, one {# row} other {# rows}}` and `Intl.PluralRules`; no i18n library is added. A missing parameter stays visible as `{name}`.
- Lookup order: override of the locale, text of the locale, override of `en`, text of `en`, the key. An override whose placeholders differ from the default is dropped when overrides are set, because the default may have changed after the override was saved.
- `useT()` uses `useSyncExternalStore`, so a language switch renders again without remounting (a remount would lose unsaved builder or grid state). Code outside React returns keys and parameters; the component translates them. The module-level `const t = strings.x` pattern is removed as screens migrate.
- The pseudo-locale wraps every English text in `⟦` and `⟧` (no square brackets: they are formula syntax). It exists for the UI rule of T4.7a2 and is never offered in the language switch.
- `vi` is typed `Record<MessageKey, string>` in T4.7e, so a key without a Vietnamese value fails the type check. The runtime fallback to English stays for stored overrides.

## D73 Errors as codes (Phase 4, T4.7d)

- `EngineError`, `StoreError` and `AuthError` carry an optional `messageId` and `params`. The id is a catalog key (`engine.*` for the engine, `errors.*` for the stores and sign-in). The UI shows the catalog text of that id in the language of the user through `errorText(e, fallback)` (`src/ui/i18n/error-text.ts`). An error without an id, or with an id the catalog does not know, shows its own English `message`: this is the fallback of SPEC 11.3.
- The English template of every id lives next to the code that throws it (`src/engine/messages.ts`, `src/store/messages.ts`), and the error's `message` is that template filled with the parameters. A unit test keeps each template equal to its `en` catalog text, with the same placeholders. The engine imports nothing from the UI (a test scans `src/engine` for imports of `ui`, React and Supabase). `src/ui/strings.ts` is gone.
- Converted: the run, version resolution and file-size errors of the engine (16 ids), every store error of `LocalStore`, `SupabaseStore` and the shared checks, and every sign-in error (the form check returns a code too). Not converted: the "invalid settings" rules inside the step modules, errors thrown by the formula parser, and the text of `planPublish`; they show their English message until a later task gives them ids. Parameters named `what` and `action` are short English phrases from the caller and are not translated.
- Texts built by logic modules at throw time are kept as text in React state, so a language switch does not change a message already on the screen.

## D74 Edited texts: table, policies and loading (Phase 4, T4.7f)

- `public.ui_texts (locale, key, value, updated_by, updated_at)`, primary key `(locale, key)`. `locale` is `en` or `vi`; the key must look like a catalog key (`nav.flows`); the value is 1 to 2000 characters. A trigger sets `updated_by` and `updated_at` from the caller, so a client cannot forge them.
- Read: `anon` and `authenticated` both read every row, through two policies. The sign-in screen needs the texts before anyone is signed in, and the texts hold no personal data. Two policies instead of one `to anon, authenticated` policy on purpose: T4.8a narrows only the `authenticated` policy to active accounts (a locked user with a valid token reads nothing, while a visitor with no session still reads the texts). Write: an admin only (`is_admin()`), which T4.8a also narrows to active admins.
- The app reads the texts once at start (`listUiTexts`, no profile needed) and applies them with `setOverrides`. A text whose placeholders differ from the default is dropped there (a text saved before a default changed cannot break a screen). If the read fails, the defaults stay. A second load after sign-in is not needed: the anonymous read already returns every row.
- `LocalStore` keeps the texts in its snapshot (`uiTexts`, optional so an older saved snapshot loads) and refuses a change from a user who is not the admin, like the database. `saveUiText` refuses an empty value; the placeholder check on save is done by the editor of T4.7g, because the store does not know the defaults.

## D75 Locking an account in the database (Phase 4, T4.8a)

- A lock must work at once for a session that is already open. An Auth ban stops new sign-ins and refreshes but does not cancel an access token that is in use, so the database refuses a locked user itself. `profiles.locked_at` (null when active) and `profiles.must_change_password` are the two new columns.
- `is_active_user()` (security definer, stable, empty search_path, like `is_admin()`) says whether the caller has a profile that is not locked. `is_admin()` is redefined as "active and admin", so every admin check of the earlier migrations excludes a locked admin without a rewrite. Every table that has row-level security also has one RESTRICTIVE policy `<table>_active_only` for `authenticated` (flows, flow_versions, flow_group_access, ref_tables, ref_table_versions, profiles, groups, group_members, run_log, ui_texts): the permissive rules of T3.3, T3.4 and T4.7f still decide who may do what, and the restrictive one adds "and the account is active". `anon` is not touched, so a visitor still reads `ui_texts` (D74). The store functions are security invoker, so these policies cover them; `visible_names()` is security definer and checks for itself.
- `locked_at` and `must_change_password` change only inside definer functions or with the service role (a trigger refuses a change when `current_user` is `authenticated` or `anon`): otherwise the admin policy of T3.4 would let an admin lock or unlock with a plain update and so skip the ban in Auth. `admin_set_locked(actor, user, locked)` and `admin_set_must_change_password(actor, user, value)` are granted to the service role only (the Edge Function of T4.8b calls them with the actor it read from the token) and check that the actor is an active admin; an admin cannot lock themselves.
- `guard_last_admin` counts active admins only, so one rule stops demoting, deleting and locking the last active admin, whoever tries it.
- `clear_must_change_password()` is for the signed-in active user and touches only the own row. `account_status()` returns the two facts about the caller's own account, also when it is locked: a locked user can no longer read the own profile, so the app needs this to say "your account is locked" instead of "no profile".
- Two tests keep the rule from rotting: every table with row-level security must have a restrictive active-only policy, and the list of security definer functions of the `public` schema must equal the reviewed list.

## D76 The Edge Function `admin-users` (Phase 4, T4.8b)

- One function, `supabase/functions/admin-users`, the only server code of the app. Actions: `create`, `reset_password`, `lock`, `unlock`, in a JSON body with `action`. It uses the service role, so it checks the caller itself: a valid token (read through Auth), a profile with role admin, and `locked_at` null. A signed-out call, the anon key, a user, and a locked admin are refused (401 or 403); the gateway also needs a valid token (`verify_jwt = true`).
- Input checks: a well-formed email, a password of at least 10 characters (the form of D-Phase 4 password rule), the role `user` or `admin`, an id that is a UUID. An existing email gives 409; an unknown user 404. Every error is `{ error: { code, messageId, params, message } }`: the UI shows the catalog text of `messageId` (`errors.account.*`), `message` is the English fallback. The function keeps its own copy of the English templates, because code outside `supabase/functions` is not part of what the CLI deploys; T4.8c adds a unit test that compares the copy with `src/store/messages.ts`.
- Lock: the database function `admin_set_locked` applies the rules (an active admin acts, not on oneself, the last active admin stays), then the function bans the user in Auth (`ban_duration` of about 100 years; `none` to unlock) and ends the sessions. If the ban fails the database lock is undone, so the two never differ. Create: Auth creates the user, the trigger makes the profile (always role user), then the function sets the role and `must_change_password` (on by default). Reset: Auth sets the password, the flag is set, the sessions end.
- Ending sessions: an Auth ban refuses new sign-ins and refreshes, a password change does not end other sessions, and an access token already issued stays valid for its hour. So migration 12 adds `admin_end_sessions(user)` (service role only), which deletes the user's rows in `auth.sessions` and their refresh tokens; the integration test shows the old refresh token is refused after a lock and after a reset. A locked user's token that is still valid is refused by the database itself (D75).
- The function has no dependency: it calls Auth and the REST API with `fetch`. The first version imported `@supabase/supabase-js` from npm, and the local Edge Runtime could not verify the TLS certificate of the registry in this environment (the boot error is in PROGRESS.md under the T4.8b log); not needing a download at boot is also faster and safer on a real deployment.
- `npm run test:functions` (G6) starts the full local stack (with the Edge Runtime), applies the migrations from zero, waits for the function, and runs `integration-functions/admin-users.test.ts` (14 tests); `npm run gates` ends with it. `test:db` leaves the Edge Runtime out like gotrue, postgrest and kong.

## D77 Flow parameters: the definition format (Phase 4, T4.9a)

- The definition gets `schemaVersion` 2, which may carry `parameters`. The app reads versions 1 and 2 (`SUPPORTED_SCHEMA_VERSIONS`); the JSON schema says `enum: [1, 2]` and the error for another version names both. A new flow, and every flow without parameters, stays in version 1 (`BASE_SCHEMA_VERSION`): nothing is rewritten.
- A stored definition is never changed. A published version cannot change in the database, and `flows/monthly-timesheet.flow.json` must stay byte for byte as it is. `validateFlow` therefore returns a normalized copy (`parameters: []` for an older definition) and never touches its input; a test loads the real acceptance file and checks both.
- The only code that writes version 2 is `withParameters(definition, list)`: it returns the definition unchanged for an empty list on a definition that has no `parameters` key. The builder (T4.9c) must call only that helper, and only when the user adds, edits or removes a parameter. If opening a draft added `parameters: []` or the version, the dirty check (canonical JSON against the saved definition) would show "Unsaved changes" on every draft.
- A version 1 definition that has a `parameters` key is refused (`engine.paramNeedsV2`), not ignored, so nobody loses parameters without being told.
- A parameter: `key` (letters, digits, underscore, not starting with a digit, at most 40 characters, unique without regard to case because DuckDB identifiers ignore case and the keys become columns of the `params` view), `label` (not empty), `type` (date, text, number, list, boolean), `required` (boolean), `default` (must fit the type: a real ISO date, a finite number, a boolean, text, or one of the options), `options` (a list needs at least one, different and not empty), `help` (text). Every validation error names the parameter and has a message id (`engine.param*`) with `en` and `vi` texts.
- Decisions for T4.9b, recorded now: `PARAM("key")` compiles to a scalar subquery on the one-row `params` view, so the type comes from one place and no value is ever written into the SQL text. DuckDB cannot create a view with no column, so a flow without parameters has no `params` view (or a placeholder column); the SQL step says so if its query uses `params` anyway, and its allow-list of table names accepts `params`.

## D78 Parameters in a run: typed literals and a `params` CTE (T4.9b)

- Changed from the plan in D77: no `params` view and no scalar subquery. `PARAM("key")` compiles to a typed SQL literal (`CAST('2026-09-15' AS DATE)`, `CAST(2 AS DOUBLE)`, a quoted text, `TRUE`). Reason: a view is one more object to create and drop, DuckDB cannot make a view with zero columns, and the literal already comes from one place (`parameterLiteral`). A text value is always quoted by `quoteString`, so a value is never read as SQL; a test runs a value with a quote and `OR 1=1`.
- The SQL step gets a `params` CTE with one row and one column per parameter, added next to `in1`, `in2`. A flow without parameters has no `params`; a query that reads it gets an error that says to add a parameter. `checkSqlText` needed no change because it forbids words, not table names.
- `runFlow` takes `parameterValues` (by key) and checks them with `resolveParameterValues` right after the flow is validated and before any step runs: a required value must be given (`null` and empty text count as missing), the value must fit the type, a list value must be an option. Errors are coded (`engine.paramMissing`, `engine.paramWrongType`, `engine.paramNotOption`) with English and Vietnamese texts. The engine does not apply defaults; the Run screen fills them (T4.9e).
- A list parameter is text in formulas. `PARAM` finds the key without regard to case, like the key rule of D77. An unknown key is a formula error at the key that names it and lists the known keys.

## D87 Why dragging a card is jerky and a card can disappear (T6.1)

Measured with `npm run perf:canvas` (numbers in `docs/CANVAS_PERF.md`, a production build with the render counters of `src/ui/builder/render-counter.ts`, on only when `VITE_PERF_COUNTERS=true`). The task changes no behaviour of the app.

- **Cards disappear.** During a drag every card has `visibility: hidden` in its inline style. React Flow hides a node that has no measured size, and `canvas.tsx` builds the controlled `nodes` array again from the definition on every pointer move without `measured` or `width`/`height`, so the nodes are hidden until its resize observer measures them again. The measurement sees 0 visible cards of 12, 60 and 70 in the middle of the drag, and all of them before and after.
- **Jerky.** Each pointer move calls `moveStep`, which makes a new definition in `BuilderScreen` state. One drag of 60 moves renders `BuilderScreen`, `SettingsPanel` and `StepList` 61 times each and every `StepCard` 61 times (1,454 card renders with 12 steps, 7,262 with 60, 8,472 with the 70 steps of the timesheet flow), because `nodes` and `edges` depend on the whole definition and on the selection, and `StepCard` is not memoized.
- **The "12-step timesheet flow" of T6.1 is 70 steps.** `flows/monthly-timesheet.flow.json` has 70 steps and 77 edges. The script measures the real flow (70 steps) and two generated flows of 12 and 60 steps, which are the sizes of the budgets in SPEC 13.1.
- **Frame times in headless Chromium are not the problem on their own** (p95 17 ms, the 60 Hz frame, in all three runs, because the mouse moves are paced by the test protocol). The fix is therefore judged by the three other measures: no hidden card, one change of the definition per drag, and the render counts. T6.2 keeps the held card in React Flow's own state, writes it on `onNodeDragStop`, memoizes `StepCard`, and asserts the budgets with a margin.

## D88 The fix of the drag (T6.2)

- `canvas.tsx` keeps the position of a held card in its own state (`held`). A pointer move with `dragging: true` only changes `held`; the drop (a position change with `dragging: false`, also the arrow keys) writes the definition once. One drag is one change of the definition: `BuilderScreen`, `SettingsPanel` and `StepList` render 2 times during a drag (the selection and the drop) instead of 61, and the cards that are not held keep their objects, so only the held card renders for a move (85 card renders with 12 steps instead of 1,454; 181 with 60 instead of 7,262).
- The measured size of each card is carried into every rebuilt `nodes` array with `getInternalNode(id).measured`. `getNode` is not enough: it returns the user node, which has no measured size, so the card would stay hidden (the cause of D87). `StepCard` is memoized.
- `e2e/canvas-drag.spec.ts` (part of `npm run test:e2e`) asserts: all cards visible while held (sampled every 6 moves) and after the drop, the card at the position where it was left, the edge of the card changes during the drag, the selection and the settings panel are kept, the unsaved state is on after one drag, at most 4 renders of the three parts, and p95 frame time under 26.4 ms (12 steps) and 40 ms (60 steps), which is 20% under the budgets of SPEC 13.1 (33 and 50 ms). A published version cannot be dragged (a drag on a locked card pans the canvas). Reached in `docs/CANVAS_PERF.md`: p95 17 ms with 12, 60 and 70 steps. This is the frame rate of the headless run, so the margin is large; the test guards the hidden card and the render counts more than the frame time.

## D91 How the csv path reads a table inside a larger file (T6.16a)

DuckDB `read_csv` stays the csv reader (D10), with three changes for files that have a title block, a footer or empty lines:

- **The dialect is decided in the engine, not by the sniffer.** The sniffer of DuckDB takes a one-column title for the whole format (it chose `|` and one column, or failed with "not possible to detect the dialect") when the rows have different widths. The engine scans the lines once: the delimiter is the one of `, ; tab |` that splits the most lines (a tie goes to the comma), and the width is that of the widest line (a delimiter inside quotes can only make it larger; the cells that are not there are empty). Then `read_csv` gets the dialect and the column list explicitly (`auto_detect = false`, `skip = 0`, `null_padding`).
- **Rows are numbered by the line of the file.** DuckDB leaves empty lines out of a table, so the n-th row is mapped to the n-th line that is not empty. When the two counts differ (a quoted cell that holds a line break) the order of the rows is kept, and then "header row", "rows to skip" and the row number column count rows, not lines.
- **The region, the stop rule and the rows to ignore are SQL** over those rows: the first and last column are positions; a marker is looked for in the named column or in every column of the row; "N empty rows in a row" is evaluated over the list of all line numbers, where a line that is not in the table is empty; a row to ignore is not empty.

The xlsx reader gets the same rules in its row loop. It stops reading the file at the stop rule (`LoadStats.rowsRead` shows how many rows it took), and it counts a gap in the row numbers as empty rows, because the sheet XML does not hold empty rows.

## D121 A limit on the number of flows of a user (admin)

- `User.maxFlows` (null or missing: no limit; 0 to 10,000) and `profiles.max_flows` (migration 20, with a check). The admin edits it in the Users dialog, in the field "Flows this user may create" (an info button says that empty is no limit, a deleted flow does not count and an admin has none); the field is shown only while the role is User, and a form with something other than a whole number from 0 to 10,000 says what to type.
- What counts: the flows the user owns that are not deleted, personal or shared. What is refused: a new flow and a copy of a shared flow. Restoring a deleted flow (admin only) is not checked. An admin has no limit whatever the value.
- Enforced in the database by a trigger `flows_enforce_limit` (before insert on `flows`, `security definer`, so the count is exact and does not depend on what row-level security shows the caller), not in `create_flow` and `copy_flow`: a direct insert is covered too. The message is the same in the trigger, in `LocalStore` and in both catalogs (`errors.flowLimit`): "You have reached the limit of {max} flows that the admin set for you. Delete a flow, or ask the admin to raise the limit." The trigger function is `security definer`, so the list of reviewed definer functions in `120-account-lock.test.sql` has it, and `010-tables.test.sql` has the new column.
- Tests: `supabase/tests/database/190-max-flows.test.sql` (21 assertions), `src/store/local-store.test.ts`, `supabase-mapping.test.ts`, `admin-logic.test.ts`, and three e2e journeys in `e2e/admin.spec.ts`.
